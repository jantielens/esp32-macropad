## Goal and Scope

Prepare the Inkplate 6 Flick LVGL spike for a release branch without allowing
Inkplate-specific presentation policy to become a shared display contract.
The final release candidate must have correct installer metadata, bounded and
synchronized presentation settings, truthful refresh requests, verified
failure handling, and a clear experimental support statement.

The work is divided into two tracks:

* Stabilize the Inkplate feature and its release contract
* Extract platform-generic improvements into independently testable commits

The four generic candidates are PSRAM-first data-stream allocation, dynamic
pad-cache lifetime management, PNG dimension limits with icon capability
advertising, and opt-in `DISPLAY_DISABLE_ANIMATIONS`. Other spike changes remain
coupled to the Inkplate driver and presentation contract until a later
controller-capability design is implemented.

## Completed Baseline Work

The board registry now distinguishes the two Inkplate 6 Flick firmware profiles:

* `inkplate6flick`: Low-power, sleep-first e-paper firmware without LVGL and
   with the OTA-enabled partition.
* `inkplate6flick-lvgl`: Interactive, always-on LVGL firmware with the larger
   no-OTA application partition.

Commit: `chore(settings): clarify inkplate firmware profiles`

Changelog: No. This configuration-comment change does not alter firmware
behavior or user-visible release contents.

> [!IMPORTANT]
> Do not merge this spike as six original commits. Implement the stabilization
> fixes first, then extract each generic candidate as a small, independently
> reviewed commit with its own tests.

## Commit and Changelog Policy

Create each suggested commit only after its focused validation succeeds. Keep
the `Unreleased` section of `CHANGELOG.md` current in the same commit for every
user-visible feature, behavior change, bug fix, target or capability correction,
and documentation change. Internal refactors and test-only commits do not need a
changelog entry unless they correct user-visible behavior.

Use concise, categorized release-note wording. The final release-preparation
commit consolidates the accumulated `Unreleased` entries under version `1.32.0`;
it must not omit an earlier user-visible change.

## Release Readiness Phases

### Phase 1: Correct Public Target and Release Metadata

Resolve the contradictory target and installer contract before building release
artifacts.

1. Correct the Inkplate target capability list in
   `src/boards/inkplate6flick-lvgl/metadata.json` so it does not advertise MCP
   while `HAS_MCP` is false.
2. Choose one B/W target model and apply it consistently:
   * Remove `src/boards/inkplate6flick-lvgl-bw/metadata.json` and the README
     entry if B/W is only a runtime presentation mode of `inkplate6flick-lvgl`.
   * Alternatively, restore the full board directory, target registry entry,
     board overrides, CI coverage, and build artifact for a distinct B/W target.
3. Add an `Unreleased` section to `CHANGELOG.md`. State that the Inkplate target
   is experimental, identify its supported presentation controls, and call out
   the no-OTA partition limitation.
4. Update `docs/dev/display-touch-architecture.md` with the Inkplate display and
   Cypress touch drivers. Document the buffered framebuffer and coalesced
   presentation model.

Validation:

* Check that every installer metadata board is a valid `config.sh` target.
* Run the existing installer/asset metadata checks.
* Review generated installer board cards for only advertised capabilities.

Suggested commit: `fix(inkplate): align target metadata and release docs`

Changelog: Yes. State that experimental Inkplate 6 Flick support and its
advertised capabilities were corrected, including any target consolidation.

### Phase 2: Bound and Synchronize Presentation Configuration

Make configuration safe regardless of whether it originates from defaults,
NVS, MCP, or the portal.

1. Define named minimum, maximum, and default constants for the refresh
   cadence, B/W partial refresh period, grayscale settle time, and any other
   presentation interval. Keep controller-specific physical limits in the
   Inkplate driver or an Inkplate-specific configuration module.
2. Replace duplicated default assignments in `config_manager.cpp` with one
   helper or canonical defaults structure shared by initial configuration and
   missing-NVS fallback.
3. Validate all presentation values in `config_manager.cpp` on load. Reject or
   clamp values outside their supported range, particularly zero refresh
   intervals.
4. Apply the same validation in the portal configuration endpoint before
   persisting values. Ensure MCP configuration updates take the same validated
   route.
5. Introduce a synchronized presentation-settings snapshot. The web task may
   publish a new snapshot, while the LVGL and present tasks read a coherent,
   lock-protected or atomic copy. Do not read mutable `DeviceConfig` fields
   concurrently across tasks.
6. Add host tests for default parity, lower and upper bounds, zero rejection,
   persisted invalid values, and portal/MCP validation behavior.

Validation:

* Run focused configuration and action tests.
* Build `jc1060p470c-sd` to confirm ordinary boards compile with the added
  shared configuration logic.
* Build `inkplate6flick-lvgl` and manually submit valid and invalid values from
  the portal.

Suggested commit: `fix(epaper): validate and synchronize presentation settings`

Changelog: Yes. Describe safer persisted e-paper presentation settings and
validated refresh cadence values.

### Phase 3: Make Refresh Operations Truthful and Responsive

Repair the runtime behavior around manual refreshes and long e-paper waveforms.

1. Change `display_refresh_action.cpp` and the presentation component endpoint
   to distinguish queued, unavailable, and failed refresh requests. Return a
   failure status instead of unconditional success when the selected display
   cannot accept the request.
2. Define a driver initialization-success contract. When Inkplate framebuffer,
   mutex, or snapshot allocation fails, mark the display unavailable and expose
   the reason through diagnostics rather than continuing as if the panel works.
3. Shorten the framebuffer mutex critical section in the Inkplate driver.
   Snapshot or swap a completed framebuffer while locked, release the lock, and
   call blocking `display()` or `partialUpdate()` outside the lock. Preserve
   writes that arrive during the waveform as pending for the next present.
4. Add focused tests for refresh queue results and initialization failure paths.
   Add a test seam for the presentation snapshot handoff if practical.
5. Perform hardware validation for full refresh, partial refresh, rapid touch,
   wake behavior, icon replacement, and repeated settings changes. Include a
   long-running ghosting and PSRAM fragmentation soak.

Validation:

* Run the host test suite and the action catalog completeness test.
* Build `inkplate6flick-lvgl`.
* Record hardware validation results in the spike notes before release review.

Suggested commit: `fix(inkplate): harden presentation lifecycle and refreshes`

Changelog: Yes. Describe improved Inkplate refresh reliability and truthful
manual refresh status.

### Phase 4: Preserve Board Isolation

Ensure e-paper code and portal assets remain absent from non-e-paper builds.

1. Gate the `display_refresh_action.cpp` inclusion in `action_modules.inc` with
   `HAS_EPAPER_PRESENTATION`. This is the immediate containment fix.
2. Add a disabled-feature action-catalog test. It must assert that
   `display_refresh` is not registered or advertised when
   `HAS_EPAPER_PRESENTATION` is false.
3. Extend `tests/test_asset_variant_matrix.sh` with explicit
   `HAS_EPAPER_PRESENTATION` enabled and disabled variants. Assert that the
   presentation fragment and script declarations are absent from ordinary
   display bundles and present only when enabled.
4. Retain the existing compile gates around driver aggregation, routes,
   fragments, scripts, and component registration. Add focused assertions only
   where the current matrix lacks coverage.

Validation:

* Run the action catalog and asset variant matrix tests.
* Build `jc1060p470c-sd` and confirm no presentation action, route, or asset is
  emitted.
* Build `inkplate6flick-lvgl` and confirm the presentation action, route, and
  asset are emitted.

Suggested commit: `test(epaper): enforce presentation feature isolation`

Changelog: No, unless the containment change fixes a released board capability
or exposes/removes a user-visible control on an existing board.

### Phase 5: Establish a Generic Presentation Capability Boundary

Do not extend the Inkplate-specific `HAS_EPAPER_PRESENTATION` contract to future
controllers such as IT8951. Introduce a small display-driver capability boundary
before enabling another e-paper controller.

1. Add a driver capability query for full refresh and presentation controls.
   The API should represent what the selected driver can perform, not which
   controller family it uses.
2. Move generic refresh scheduling behind driver methods, such as a binding
   refresh interval and a clock-boundary refresh requirement. Remove direct
   interpretation of `INKPLATE_LVGL_MODE_BW` from shared pad-screen scheduling.
3. Keep waveform cadence, ghosting protection, and controller-specific timing
   in the owning driver or driver-specific configuration component.
4. Replace the fixed portal `bw` and `grayscale` model with driver-provided mode
   descriptors, or move the mode-specific controls into a driver-owned portal
   component. Shared portal code should expose only controller-neutral controls.
5. Derive the refresh action, REST route, and portal capability JSON from the
   selected display driver's capabilities. Retire the presentation feature flag
   as the public capability gate once all supported e-paper drivers use the
   interface.
6. Add host tests with fake capability profiles for an unsupported display, a
   B/W driver, a grayscale driver, and an IT8951-like driver with different mode
   identifiers.

Validation:

* Run capability/profile host tests.
* Build one ordinary display board and the Inkplate board.
* Review the resulting portal JSON to confirm it contains only the selected
  driver capabilities.

Suggested commit: `refactor(display): expose driver presentation capabilities`

Changelog: No. This establishes an internal extension boundary unless it ships a
new supported controller or changes existing portal controls.

## Generic Extraction Track

Each item below must be extracted into a standalone commit after it has focused
tests. Do not bundle it with driver enablement, e-paper presentation controls,
or Inkplate board metadata.

### PSRAM-First Data-Stream Allocation

1. Isolate the data-stream registry allocation changes from the original spike
   commit.
2. Preserve `HAS_DISPLAY && HAS_MQTT` gating and use the project's established
   PSRAM allocation pattern with allocation-failure handling.
3. Add registry allocation, fallback, and cleanup tests where the existing host
   seams permit them.
4. Build a representative display-and-MQTT target and a target without that
   feature combination.

Suggested commit: `perf(streams): allocate display data streams in PSRAM`

Changelog: No. This is an internal allocation change unless a user-visible
stability or capacity improvement is intentionally claimed in the release notes.

### Dynamic Pad-Cache Lifetime Redesign

1. Extract the immutable, dynamically sized pad-cache changes from the spike.
2. Restore coverage removed with `test_pad_cache_transaction.cpp`, or replace it
   with equivalent tests for active readers, replacement, delete/rebuild,
   template resize, allocation failure, and retained last-known-good state.
3. Verify ownership and synchronization rules under concurrent readers before
   merging the generic commit.
4. Build `jc1060p470c-sd` and run the complete host suite.

Suggested commit: `refactor(pads): use dynamic immutable pad-cache snapshots`

Changelog: No. The commit must be behavior-preserving and fully covered by
regression tests.

### PNG Dimension Limits and Icon Capability Advertising

1. Separate PNG header dimension validation and icon-size capability changes
   from e-paper behavior.
2. Keep limits generic, documented, and enforced before decode/allocation.
3. Add upload, load, oversized-image rejection, and advertised-limit regression
   tests.
4. Verify the API continues to report a capability appropriate to each board.

Suggested commit: `fix(icons): validate PNG dimensions before decode`

Changelog: Yes. State that invalid or oversized PNG icon uploads are rejected
before decode and that icon capability reporting is accurate.

### Opt-In Display Animation Disablement

1. Extract `DISPLAY_DISABLE_ANIMATIONS` as a generic slow-display policy.
2. Keep the default behavior unchanged for existing boards.
3. Document the compile-time flag and add a small compile or behavior test for
   the enabled path.
4. Do not associate the feature with Inkplate names, modes, or portal controls.

Suggested commit: `feat(display): allow animations to be disabled at compile time`

Changelog: Yes. Document the new opt-in compile-time display animation policy.

## Release 1.32.0 Integration

Create `release/1.32.0` from the intended release base after the stabilization
commits are complete. Apply only the independently validated generic commits
selected for this release; explicitly defer the rest instead of carrying them
implicitly from the spike branch.

1. Rebase or cherry-pick the approved commits in dependency order: target and
   metadata corrections, configuration safety, presentation lifecycle, isolation
   tests, then selected generic extractions. Keep the driver-capability refactor
   separate unless a second e-paper controller is shipping in 1.32.0.
2. Reconcile all `Unreleased` entries into categorized 1.32.0 release notes.
   Label Inkplate 6 Flick support experimental, state its no-OTA limitation,
   and list only user-visible generic improvements that are included.
3. Update `src/version.h` to `1.32.0` and update any versioned portal or static
   asset references required by the release workflow.
4. Re-check `README.md`, display/touch architecture documentation, compile-time
   flag documentation, web portal documentation, installer metadata, board
   capability descriptions, and the changelog for consistency.
5. Run the full host suite, action catalog completeness test, asset variant
   matrix, `./build.sh jc1060p470c-sd`, and
   `./build.sh inkplate6flick-lvgl`.
6. Record the required Inkplate hardware evidence: display waveforms and
   ghosting, touch and wake, icon lifecycle, persisted settings, and a
   long-running PSRAM soak.
7. Require a clean worktree and a final review before creating the release tag.

## Release Gate

The release branch is ready only when all of the following are true:

* Installer metadata, target registration, README, and changelog agree.
* Presentation settings have canonical defaults, bounds, and cross-task safety.
* Full refresh requests report their actual queue outcome.
* The driver handles initialization failure visibly and presents outside the
  framebuffer lock.
* Action and asset matrix tests prove e-paper features do not bleed into other
  boards.
* The generic candidates are either extracted with their own tests or explicitly
  excluded from the release branch.
* The full host suite, action catalog check, asset variant matrix, and builds
  for `jc1060p470c-sd` and `inkplate6flick-lvgl` pass.
* Hardware validation covers display waveforms, ghosting, touch, wake, icons,
  settings persistence, and a long-running PSRAM soak.
