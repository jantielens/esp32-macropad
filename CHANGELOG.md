## Overview

All notable changes to this project will be documented in this file.

The format is based on [Keep a Changelog](https://keepachangelog.com/en/1.0.0/),
and this project adheres to [Semantic Versioning](https://semver.org/spec/v2.0.0.html).

## [Unreleased]

### Added

* **Matrix Rain native Extension**: ESP32-P4 pads can now render configurable green character streams using firmware fonts directly in an RGB565 canvas. Per-button settings control the font, falling speed, stream density, trail length, and animation cadence.
* **Block Drop Clock native Extension**: ESP32-P4 pads can now host a responsive pixel-art clock with a live falling-block playfield. The Extension adapts its grid to the containing button, supports time bindings, optional burn-in shifting, and a configurable playfield speed. Its catalog metadata, preview, and development guide are included with the package.
* **RGB565 sprite blitting for native Extensions**: the canvas host API now copies caller-owned RGB565 sprites into exact destination rectangles with clipped nearest-neighbor scaling. This gives animated Extensions a compact, reusable primitive for pixel-art assets without per-source-pixel canvas calls.
* **FireBeetle 2 ESP32-C6 AHT10 sensor-node target**: the new `firebeetle2-esp32c6-aht10` target supports DFRobot's battery-powered FireBeetle 2 ESP32-C6 v1.2 with an AHT10 on GPIO19/GPIO20. Its built-in LED on GPIO15 remains unconfigured. The target reads the onboard GPIO0 2:1 LiPo divider and uses the `huge_app` partition, so it does not support OTA updates.
* **Reusable battery ADC sensor adapter**: battery-powered boards can enable `HAS_SENSOR_BATTERY_ADC` and configure their ADC pin, divider, calibration multiplier, and averaging count. The adapter publishes battery voltage and an interpolated single-cell LiPo percentage through API, MQTT/Home Assistant discovery, and BTHome BLE telemetry.
* **Guided Coffee Scale brew templates**: built-in Free Pour and V60 Pour-Over flows now use consistent short labels and phase guidance, while Advanced V60 provides a 16 g / 250 g three-minute guide with cumulative water targets, flow targets, timed bloom and second-pour stages, and a manual final finish. Brew templates support phase instructions, `target_time_s` advisory targets for any stage, and automatic advancement only for `auto_time` stages. New `[brew:advance_state]` and `[brew:stage_status]` bindings let pads distinguish manual from automatic stages and present compact live pour/timing guidance.

### Changed

* **Native Extension ABI 16**: Extensions now use grouped host services exclusively, canvas text selects firmware fonts by name, and each External Widget placement can define its own tick interval. All shipped native Extension packages are rebuilt for the new ABI.

### Fixed

* **Native Extension sprites now stay within their target cells**: exact-size RGB565 blitting prevents one-physical-pixel trails on pad sizes whose grid cells are not an integer multiple of a sprite's source dimensions.
* **Coffee Scale calibration weight accepts Numeric Rocker step values**: the **Adjust calibration weight** action editor now accepts `{step}` placeholders so the same numeric-rocker workflow works for calibration deltas as it does for other adjustment actions.
* **Timer actions are available in the Pad editor again**: the action catalog once again exposes the Timer command choices required by the editor, including Toggle, Start, Stop, Pause, Resume, Reset, Set countdown, and Adjust countdown.
* **Coffee Scale brews now save reliably**: brew logs lazily create their Coffee Scale-owned `/brews` directory on the selected storage backend, initialize and persist their NVS log-ID counter, and report storage write failures accurately instead of claiming every save succeeded. Starting a brew now waits for its deferred tare to complete before accepting the first-pour weight threshold, preventing an existing cup weight from immediately starting the timer.
* **Portal navigation no longer silently omits late-registered fragments**: the fixed component registry capacity increases from 32 to 64 entries, restoring the Coffee Scale **Brew Templates** page on feature-rich boards. A board-matrix test now evaluates every configured board's active portal registrations and fails if any exceed the registry limit.

## [1.25.0] - 2026-08-12

### Added

* **Native Extensions for ESP32-P4 boards**: ESP32-P4 builds now reserve two 56 KiB small slots and one 120 KiB large slot for trusted, flash-mapped RISC-V Extensions. The Device portal includes an Extensions manager with slot-specific upload, replacement, enable/disable, deletion, staging, reboot-pending, and ABI-incompatibility status. Each package is a signed `id@version.ext` upload file containing a relocation-free RISC-V ELF plus a 64-byte ECDSA P-256 signature. Firmware accepts only packages signed by the embedded first-party public key, verifies them at staging, installation, and load time, and rejects unsigned or modified code. The Pad editor's Extension widget selects an enabled package, passes up to 511 bytes of per-button configuration, marks Extension buttons with `EXT`, and lets the package handle or pass through tap and long-press events. Extensions can run one cooperative worker per package and resolve live binding templates in their own pad context, including named `[pad:]` bindings. The GitHub Pages installer catalogs the latest stable packages with a summary, configuration usage, and a direct `.ext` download. Developer samples and [the Extension guide](docs/dev/extensions.md) document the versioned host ABI, package signing, flash-mapping constraints, and lifecycle callbacks.
* **Voice Assistant device class**: `esp32-p4-lcd4b-voice` captures microphone audio and sends bounded 16 kHz WAV recordings to an Azure AI Foundry transcription deployment. Voice actions support manual recording, one-tap recording until detected trailing silence, manual stop, and recording cancellation; `[stt:status]` and `[stt:text]` bindings make the result available to follow-up actions such as MQTT Publish. Automatic capture exposes per-action trailing-silence and microphone-RMS threshold settings. Transcription has a fixed 30-second deadline, below the 60-second action-continuation limit, does not retry automatically, and reports provider timeouts as `Azure request timed out`. The Voice Assistant portal page stores the Azure host, deployment, optional ISO language, and write-only API key in NVS.
* **Azure Text-to-Speech for Voice Assistant**: the Voice Assistant portal now stores separate Azure TTS host, deployment, API key, optional two-letter language, optional verbatim Azure instructions, and default `alloy` voice settings. The new Speak text action accepts bindable text plus optional voice and volume overrides, requests MP3 audio from an Azure `gpt-4o-mini-tts` deployment, and plays it directly from a bounded PSRAM buffer. New requests stop current speech and prevent stale downloads from playing later.
* **Ordered action continuations and Delay action**: action arrays can now pause for an asynchronous action and resume their remaining actions on the normal dispatch task without blocking the device UI or main loop. The first built-in consumer is **Delay**, which waits for a required whole-number duration from 1 to 55,000 ms before continuing the current list. Up to three pausable actions can be pending device-wide at a time by default; another pausable action stops its action list and logs a clear warning when all continuation slots are occupied.
* **Microphone input abstraction and ESP32-P4 driver**: audio-input boards now expose a board-neutral API for one-task-at-a-time capture of native interleaved PCM frames. The `esp32-p4-lcd4b` target enables the ES7210 microphone ADC through the existing ES8311 I2S transport, starting RX only while a caller owns a capture session. The abstraction leaves recording, encoding, storage, and network delivery to its callers.
* **Demand-driven microphone level bindings**: audio-input display boards now expose read-only `[audio:input.rms]` and `[audio:input.peak]` bindings as 0-100 sound levels, plus `[audio:input.active]` to report whether the microphone meter is currently sampling. Sampling starts only while one of these bindings is resolving on a visible button, so boards and pads that do not use the feature do not spend I2S or CPU time on microphone reads.

### Changed

* **ESP32-C3 sensor target omits runtime hardware-button actions**: `esp32c3-withsensors` retains GPIO9 boot-hold configuration mode but no longer includes configurable tap/hold actions, MQTT-triggered action chains, or their portal and MCP controls, keeping its firmware within the 2 MB OTA application partition.
* **Action modules now own their full contracts**: each built-in action keeps its parse, serialization, dispatch, availability, validation, binding traversal, and portal/MCP catalog metadata together in one self-registering module. The action registry now routes all shared consumers, while device-class actions remain compiled only through their owning class aggregators.
* **Action editor UX is now consistent across the portal and MCP**: actions are organized into catalog-driven groups such as Navigation, Connectivity, Audio, Display, Timer, and Device, with sentence-case type and command labels. Multi-command actions expose their commands from the firmware catalog, device-class actions use the same metadata path, and Shutter Tester actions are organized by command family. Action arrays now use three fixed ordered slots with contextual labels such as **Action 1**, **Left action 1**, or **Select action 1**; empty slots collapse to **Add action** and are omitted when saved. Existing persisted action types, fields, and JSON remain unchanged, including round-tripping actions unavailable in the current build. The same catalog also supplies concrete field metadata to MCP clients, while `GET /api/info?catalog=1` supplies the portal projection.

### Fixed

* **Action configuration validation and controls now follow the registered action contract**: pad and component configuration rejects unsupported actions, action-specific invalid data, and invalid binding schemes consistently. Brightness, Volume, Device command, and Music again expose their command and value controls in the portal action editor.

## [1.24.0] - 2026-08-06

### Added

* **Music CD Player**: audio boards with the sound player enabled now discover and publish up to 32 MP3 files recursively under `/media` in stable CD order through Play/Pause, Next, Previous, and Stop actions. The Music portal page lists, streams uploads, and deletes library files without exposing transport controls. Read-only `[music:]` bindings report the current file, index, count, elapsed time, total time, status, and optional demand-driven pre-volume RMS, peak, and eight-band visualizer levels on enabled ESP32-P4 audio boards. Analysis levels clear while paused or stopped; Tone Alerts overlay active Music; MP3 Alerts remain exclusive.
* **Selectable persistent storage backends**: firmware now uses internal LittleFS by default or, when selected at compile time, a FAT32 MicroSD card as its primary persistent storage. The shared storage facade covers pad configuration, icons, sounds, and indexed data; health telemetry reports the active backend, mount state, usage, and SD card type; and reset removes only application-owned SD directories. The read-only Storage portal page and MCP storage tools report the active backend and support folder and file browsing. SD-backed firmware stops boot when the card is absent or unreadable rather than falling back to internal flash. The new `jc1060p470c-sd`, `jc3636w518-sd`, and `jc4880p433-sd` targets enable this mode for boards with on-board card slots.
* **Sparkline history backfill from Home Assistant**: a sparkline used to start empty after every reboot, which made long time windows close to useless. Each line can now name a Home Assistant entity and fetch its long-term statistics through the Recorder `get_statistics` service once the clock is synchronized. Live data always takes precedence, and the background PSRAM-stacked fetch task never blocks the UI. Configure Average reading, Latest state, or Accumulated total beside each line's live binding. The new `HAS_HA_HISTORY` compile-time flag enables the feature on boards with PSRAM, MQTT, and a display.
* **Interactive Screen Preview controls**: touch-display boards can now queue a normal on-screen tap by clicking a captured portal screenshot. The preview maps only the displayed image area to native display pixels, refreshes automatically after selecting a screen or queuing a tap, and keeps its screen selector synchronized with navigation from the device, pads, MQTT, or MCP. The new control-gated MCP `tap_screen` tool supports the same workflow. A successful request means queued, not delivered; drag, swipe, long press, and multi-touch remain unsupported.
* **Navigate through configured pads with the new Navigate Pad Sequence action**: move to the next or previous non-empty pad in numeric order, optionally wrap at the first or last eligible pad, and exclude specific pads from the sequence. The action is available anywhere shared actions are configured, including buttons, swipes, boot actions, timers, hardware buttons, MQTT triggers, and MCP pad authoring.
* **Full-screen pad tap actions**: each pad can now define up to three local actions that run when the user taps anywhere on the pad. The override takes precedence over buttons and widgets while retaining configured swipes and suppressing long-press dispatch. It uses the shared action editor, supports MQTT binding-topic collection, is available through MCP `set_pad`, and makes an action-only pad eligible for Navigate Pad Sequence. Clearing the list restores normal button interaction.
* **Timer starts now carry their mode and duration**: Start and Toggle actions explicitly select Stopwatch or Countdown, and countdown actions store their duration. Copying a button now preserves how its timer starts. Per-slot expiry-action lists remain in Timer Settings and are snapshotted when a countdown begins.
* **MCP reports the outcome of Home Assistant button actions**: `press_button` returns an execution ID when a button contains Home Assistant service actions. The new `get_ha_execution_result` tool reports whether that execution is queued, running, succeeded, or failed, including the HTTP status and a bounded response or error message. Results remain available for the four most recent executions.

### Changed

* **Audio action vocabulary**: serialized `beep` and `sound` actions are replaced by `sound_alert` with explicit `tone` or `mp3` kind. The generic action editor also adds the canonical `music` action with its four CD transport commands.
* **Audio output supports four boards at 48 kHz**: ES8311 output on esp32-p4-lcd4b, jc4880p433, and jc1060p470c now runs at 48 kHz; jc3636w518 adds PCM510xA output with stereo playback; MP3 files at every supported source rate play at the intended speed.
* **Timer configuration is intentionally incompatible with earlier Timer JSON**: mode and countdown duration moved from global Timer Settings into Start and Toggle actions. Timer Settings and the `timers` component now accept expiry actions only. The built-in Countdown Timer block and the Lap command were removed.
* **Sparkline time windows above 18 hours now work**: the stream window was stored as a 16-bit value while the pad editor accepted up to 86400 seconds, so anything past 65535 silently wrapped (a 24-hour window became roughly 5.8 hours). Windows are now 32-bit end to end, with a maximum range of seven days.
* **Sparkline sample slots are aligned to wall-clock time** once NTP is available, rather than to the time since boot. This is what lets history from Home Assistant line up with locally sampled data; the ring is reset once when the clock first becomes valid.
* **Sparkline sampling controls now use human time units** for both the chart range and the desired interval per point. The editor calculates the required point count and explains the 1024-point limit. Home Assistant history settings now sit beside the live binding they backfill, with clearer historical-value names and an explicit enable control.
* **MCP physical-device write assertions (#61)**: the new read-only `get_identity` tool returns the application SoC's immutable factory-MAC identifier together with the configured/fallback name, hostname, IP, board, and device class. MCP initialization identifies the connected device first. Authoring, destructive, and persistent configuration writes now require an exact `expected_device_id` assertion and reject missing, malformed, or mismatched values before dispatch. Tool schemas advertise the requirement centrally, successful protected writes return only the confirmed device ID, and the MCP guide documents identity-first aliases because client-generated outer namespaces are not physical identity.

### Fixed

* **Permanent display freeze when a MIPI-DSI flush collided with an in-flight copy**: `esp_lcd_panel_draw_bitmap()` returns `ESP_ERR_INVALID_STATE` when the previous DMA2D transfer has not finished, and in that case fires no completion callback. Both call sites ignored the return value, so `lv_display_flush_ready()` was never called and LVGL waited forever. Both paths now release LVGL and log the failure, and the existing PPA-rotate error path also clears the in-flight flag that had stalled pad polling.
* **MIPI-DSI cyan display flicker from health telemetry**: PSRAM largest-free-block telemetry is now disabled on continuously scanned MIPI-DSI framebuffers instead of walking the PSRAM heap. Internal largest-block telemetry is sampled on the timer daemon at most every 30 seconds and read from a cache, so health bindings and `/api/health` no longer walk an allocator pool on the LVGL task. Health history records only safe counter metrics, and a host-test guard rejects new telemetry pool walks that could starve display scan-out. Safe free and minimum memory metrics remain live; use a pipe fallback with `[health:psram_largest]` on MIPI-DSI boards.
* **Reclaimed a wasted DPI framebuffer on every ESP32-P4 MIPI-DSI board**: the panel was configured with `num_fbs = 2`, but the second framebuffer was allocated and never scanned out. Dropping to one framebuffer frees roughly 1.0 MB of PSRAM on esp32-p4-lcd4b, 0.77 MB on jc4880p433, and 1.2 MB on jc1060p470c, and halves the work done when the screen saver blanks the panel.
* **PNG button backgrounds render correctly on first load and refresh (#57)**: LVGL's bundled PNG decoder returns an owned draw buffer rather than a packed pixel pointer. The image-fetch decoder now reads RGBA pixels from that buffer using its validated row stride and releases it through LVGL on every success and error path, preventing garbage pixels, horizontal bands, out-of-bounds reads, and leaked pixel storage. Alpha remains intentionally discarded when converting backgrounds to RGB565.
* **Device configuration imports preserve each pad's template and actions**: full-device import now restores the imported pad's template selection and pad-level action list before saving it. Pad saves use an immutable snapshot while their asynchronous requests run, process sequentially, report the pad that failed, and reload the editor once only after every checked request completes. This prevents imports from saving a later pad's layout, template, actions, or icons into an earlier pad.
* **Unavailable Timer controls now fail instead of reporting success**: Stop, Pause, Resume, and Reset propagate the Timer engine's result through shared action handling and MCP controls. A valid timer ID therefore returns a clear error before the engine is initialized or when its mutex cannot be created, rather than claiming that a control operation succeeded.
* **Accepted Home Assistant service actions are delivered deterministically**: a fixed three-entry FIFO replaces the overwrite-prone single pending slot, so rapid button presses retain their order or fail explicitly when capacity is exhausted. Mixed Home Assistant and local actions preserve their configured order, every tracked execution reaches a terminal result, and both connection setup and response waits use a four-second timeout.
* **Home Assistant service actions now reject invalid authoring before a pad is saved**: the shared MCP and web portal validator requires a domain-qualified entity ID, a bare service name, and an optional JSON object encoded as a string. Qualified services such as `media_player.media_play_pause` return a correction using the bare service segment. Service storage now accepts names up to 63 characters, including `media_previous_track`, without truncation. The MCP capability manifest documents the same contract and includes a valid media-player example.
* **Home Assistant history requests now stay aligned for arbitrary sparkline intervals**: point intervals that were not an exact number of seconds (for example, 24 hours divided across 255 points) were truncated before reconstructing the Recorder request timestamps. The tiny per-point error accumulated across the Unix epoch and could shift the requested window by weeks, producing repeated "no statistics in window" responses.
* **Sparkline auto-scaling no longer breaks on gaps**: empty slots were included in the min/max computation, which could collapse or distort the Y-axis range. Non-finite slots are now skipped.
* **The first sample in a sparkline stream is no longer written to the wrong slot**, which caused a spurious point at the right edge of a freshly created chart.
* **Deferred portal and MCP work no longer leaks stale results or accesses expired requests**: the web-to-main-loop and web-to-LVGL dispatch paths now use a shared fixed-buffer, single-slot completion model with static internal-RAM semaphores. Oversized and invalid requests fail explicitly, timed-out requests retain their slots until their consumers finish, and deferred previews own copied request data through completion. Timed-out screenshot captures release payloads exactly once on the LVGL task. Host tests cover contention, timeout boundaries, cleanup, result isolation, and deferred preview lifetime.
* **Evicted pads no longer show a bare background frame on return**: screen navigation now builds the newly selected screen before its first LVGL render pass, so a pad whose cached arrays were evicted does not expose its empty background while buttons are rebuilt. The normal end-of-pass refresh is skipped for that one iteration.
* **jc1060p470c reclaims measured internal-RAM stack headroom**: runtime high-water measurements under portal, MQTT, pad, and MP3 playback load reduced the Arduino loop task from 8 KB to 6 KB and AsyncTCP from its 16 KB default to 8 KB. Both retain more than 2.6 KB of minimum observed headroom; LVGL and audio stacks remain unchanged.
* **ESP32-P4 recovers LVGL IRAM for application code**: LVGL's fast-memory attribute no longer places its hot routines in P4 IRAM. The P4 uses a unified instruction/data L2 cache, so the firmware now keeps those routines in flash while retaining the existing ESP32-S3 IRAM placement. Hardware testing found no responsiveness regression.
* **jc1060p470c MIPI-DSI now uses continuous high-speed signaling**: the JD9165 driver left `disable_lp` at `false`, unlike the ST7703 panel where continuous HS mode measured faster and removed visible flashes. It is now `true` for consistency. Hardware A/B on jc1060p470c measured the two settings as FPS-neutral; this does not by itself resolve the intermittent full-screen cyan frames on that panel, which are still under investigation.

## [1.23.0] - 2026-07-28

This release rebuilds the e-paper photoframe as a **local, battery-first system**, delivered as a matched pair: a self-hosted **photo management site** that runs on your own network, and a new **firmware client** that talks to it over a small versioned HTTP API. The cloud storage backend is gone.

The organising goal was **battery life**, and the design follows from one observation: on a device that sleeps between wakes, almost all of the energy goes to the radio and the panel, so the cheapest wake is the one that uses neither. Previously the frame fetched images from a cloud storage account over the internet and worked out for itself what to show — both expensive. Now the site owns the decision and sits on the LAN. The frame makes exactly **one authenticated request per wake**, carrying a fingerprint of the picture it is currently displaying, and the site replies with a new image or with `204 No Content` meaning *keep what you have*. A `204` wake never powers the panel and finishes in roughly **29 ms**. When there is something new, it arrives over the LAN in about **1.4 seconds** rather than the 16–25 seconds a cloud fetch took over a bandwidth-delay-limited internet path, and a cache-hit refresh completes in about **3.4 seconds** — an end-to-end wake roughly **3–4× faster**, with the radio window shortened again by deferring the clock resync until after the panel has drawn.

Moving the decision to the server has a second effect: scheduling, freshness windows, one-shot photos, and expiry all become site-side policy that you can change without reflashing or even waking the device. And because the site is a real service rather than a storage account, the things a storage account could never do arrive with it — multiple frames each with their own private gallery, backup and restore, bulk upload, and post-upload editing.

The other half of battery life is not wasting energy on failure. A wake that never ends is the worst possible outcome for a battery, so every phase of a wake is now explicitly bounded, and — most importantly — a panel that fails to draw now says so instead of reporting success and updating its cache for a picture nobody ever saw.

### Added

* **Self-hosted photoframe site — a complete replacement for the cloud image backend** — the photoframe no longer depends on a cloud storage account. `tools/photoframe-site/` is a small self-contained Python service (FastAPI + Starlette + Jinja2 + Pillow) that you run on your own network — a Raspberry Pi, a NAS, an LXC container, anything that runs Docker. It stores nothing in a database: photos, per-photo sidecars, per-device settings, and the site configuration are all plain files under one data root, so a backup is a `tar` of a directory and a restore is a copy. First boot walks you through creating the admin account and your first device; from then on the web UI gives you an upload page with interactive crop and per-image tone controls, a gallery with rotation status and countdown labels, a settings page, and a device list. Ships as a container image with a `Dockerfile` and `run_local.sh` for development. See [tools/photoframe-site/README.md](tools/photoframe-site/README.md).

* **Next-image service client on the frame — one request per wake, no polling** — a new firmware client (`src/app/device_classes/epaper/epaper_next_client.{h,cpp}`) talks to the site's versioned `/api/v1/next` endpoint. The frame sends a single authenticated request per wake carrying a fingerprint of the image it is currently showing (`Photoframe-Current-Image-Key` and `Photoframe-Current-Content-CRC32`); the site answers `200` with a new image, `204` to say *keep what you have*, or `302` to redirect. On `204` the frame skips the panel refresh entirely and goes straight back to sleep. Every response carries a mandatory CRC32 over the exact transport bytes, which the frame verifies before it decodes anything, and re-verifies on every read back from the SD cache. The e-paper portal gains an image-source selector, a service base URL, a write-only bearer token field, and a single refresh interval; the persisted configuration now carries an explicit `source_mode` discriminator so slot-carousel and service mode can never be confused for one another. See [docs/epaper-guide.md](docs/epaper-guide.md).

* **Multiple frames from one site, each with its own private gallery** — the site manages any number of devices side by side. Each device gets its own bearer token, its own display profile (width, height, transport formats, JPEG quality, image transform), its own photo library, and its own rotation state, all under `devices/<device-id>/`. Photos uploaded for the kitchen frame are never shown on the hallway frame, even when the two frames have identical dimensions — device scoping is built into the storage layout and the selection index rather than applied as a filter afterwards. The frame itself is unchanged by this: it still presents exactly one token and knows nothing about devices; the site derives the device from the token. Adding a device mints a URL-safe id, creates its directories, and generates a token; the settings page shows only a short fingerprint of that token until you re-enter your password to reveal or rotate it.

* **Device and whole-site backup, restore, and transfer** — any single device or the entire site can be exported to a `.zip` bundle and imported again, which covers moving to new hardware, cloning a working configuration, and recovering from a mistake. Import is deliberately paranoid: archive entries are checked for path traversal, symlinks, encryption, and oversize content *and* re-checked for containment during extraction; every file is verified against a SHA-256 checksum table using a constant-time comparison; every image's stored CRC32 is recomputed against its actual bytes; the device id, output profile, and token are all re-validated; and the incoming configuration is loaded in a dry run before anything is committed. The apply step is atomic — the new tree is staged, swapped in under a lock, and the old tree kept as a backup — and a site import interrupted midway is completed or rolled back automatically the next time the service starts. Bundles are accepted across site versions as long as the archive schema is compatible, so taking a backup before an upgrade does not strand you. Both operations require re-entering your password, and a whole-site import replaces your credentials, so the service marks itself as needing a restart and refuses further requests until you restart it.

* **Bulk photo upload** — a new *Bulk upload* page accepts a whole selection of images at once and processes them **one at a time**, showing per-file progress and a running count, so filling a fresh frame no longer means a dozen trips through the single-upload form. Files that fail are reported individually and the rest still upload; the button then turns into *Retry failed* and retries only the ones that did not make it. Because uploads are strictly sequential and reuse the existing single-image endpoint, a large batch places no more load on the server than a person uploading by hand.

* **Edit a photo's caption and lifetime after upload** — the gallery gains an *Edit photo* panel on each card, so a typo or a wrong lifetime choice no longer means deleting and re-uploading. You can rewrite the caption and switch the photo between *Show once*, *Keep always*, and a fixed expiry (1, 6, 12, 24, or 48 hours, one week, or one month from now), or leave the lifetime untouched. The image and all of its processing metadata — crop rectangle, tone adjustments, and the encoded transport variants — are preserved exactly, so editing is genuinely free.

* **Panel health diagnostics on the e-paper status page** — the reTerminal E1003 driver now retains counters across deep sleep for HRDY timeouts, the phase in which the most recent timeout occurred, the initial HRDY pin state seen at initialisation, controller recovery attempts and their outcomes, and cumulative HRDY wait time, all surfaced in the portal's e-paper status component. A healthy device stays silent; a frame that is intermittently struggling can be identified from the portal instead of by watching a serial log, and a long unattended run can be told apart from one that quietly recovered a few times along the way.

* **Published conformance bundle for the next-image protocol** — `docs/dev/photoframe-next-image/` now contains everything needed to build an independent client, server, or bridge: a normative contract document, an OpenAPI description, a machine-readable assertion list, and a set of golden conformance vectors (valid and deliberately invalid) for the reTerminal E1003 landscape profile. Two runnable checkers ship with it — `verify_vectors.py` validates an encoder against the golden bytes, and the site's `conformance_adapter.py` executes every service-role assertion against a live instance. A host test (`tests/test_photoframe_vector_drift.sh`) re-runs the vector producer against the production encoder on every test run, so an optimisation can never silently change the bytes on the wire.

* **Optional remote access over Tailscale** — for reaching the site from outside your own network, the README documents an end-to-end Tailscale setup. **Serve** is presented first and recommended: it keeps the site private to authenticated members of your tailnet. **Funnel** is documented as the exception for when a client cannot join the tailnet, with an explicit warning that it publishes the site — including its login, upload, and site-import endpoints — to the public internet, and guidance to complete the initial admin setup on your trusted LAN first, rebind the container to loopback, and enable secure cookies. Companion sections spell out what protects the service on a hostile network and what does not.

### Changed

* **The photoframe backend is now local — a breaking change with no migration path (breaking)** — the cloud service, its deployment script (`deploy/azure-deploy.sh`), its startup configuration, and its benchmarking harness are removed, and the example configuration file goes with them. There is no automated migration: the storage layout is different (photos now live under a per-device directory tree instead of a single shared pool, alongside per-image sidecars that did not previously exist), the frame is configured with a service URL and a bearer token instead of a storage URL, and the site's own configuration is created by its first-boot setup wizard. **Treat 1.23.0 as a greenfield redeploy**: stand the new site up, create your device, upload your photos again, then point the frame at it. Frames left pointing at the old backend keep working in slot-carousel mode and are unaffected until you switch them over.

* **NTP resynchronisation is deferred until after the panel has been drawn** — on a battery-powered frame the wake budget is dominated by the radio, and the SNTP client previously competed with the image download for it, intermittently costing several seconds. The clock resync now happens *after* the refresh completes, runs only when it is actually due rather than every wake, is bounded by an explicit maximum wait, and is always torn down with an explicit stop before the device sleeps — leaving a clean network stack at sleep time. The static-IP fields in the portal and the setup wizard now explain why they matter on battery devices: skipping DHCP negotiation measurably shortens the connect phase.

* **Image integrity verification is always on; the `EPAPER_VERIFY_CRC32` build flag is removed (breaking for custom builds)** — CRC32 verification of downloaded payloads used to be opt-in at compile time, which meant it was possible to ship a build that decoded unverified bytes straight into the panel buffer. Verification is now unconditional and lives in one shared place: `epaper_transport_crc32.{h,cpp}` provides the single checksum implementation used by the driver, the service client, and the host tests, replacing a driver-local copy, and `epaper_media_validation.{h,cpp}` holds the one set of format checks for G16P, JPEG, and G16Z payloads. Custom board configurations that defined `EPAPER_VERIFY_CRC32` should simply drop the define. See [docs/compile-time-flags.md](docs/compile-time-flags.md).

* **The site reuses one image conversion for both grayscale transport formats** — devices that request both the uncompressed (`G16P`) and deflate-compressed (`G16Z`) grayscale formats used to run the full decode, crop, tone-mapping, and quantisation pipeline twice. The compressed variant is now produced by deflating the exact bytes of the uncompressed one, so an upload does the expensive work once. This meaningfully shortens upload processing on modest hardware, and because both variants come from the same source bytes they cannot drift apart. Thumbnails and transport bytes are byte-for-byte identical to before, with hash-level regression coverage and the vector drift guard to keep it that way.

* **Hardened request handling for internet-facing deployments** — the site enforces explicit limits on everything a caller can send: separate size ceilings for form posts, image uploads, and archive uploads, plus a timeout on reading the request body so a deliberately slow upload cannot tie up a worker. Decoded images are bounded by both maximum dimensions and total pixel count, which rejects decompression bombs before they can allocate, and crop geometry is validated against the source. Every state-changing form carries a CSRF token. Failed logins are throttled on three independent axes — per client IP, per account, and globally — with exponential backoff, so neither a targeted attack on one account nor a spray across many can be brute-forced. `X-Forwarded-For` is ignored unless the connecting peer is in an explicitly configured trusted-proxy list, so the throttles cannot be side-stepped or turned against another user by a forged header. Pillow is upgraded to 12.3.0 in the same change.

### Fixed

* **Frames no longer report a successful update when the panel never actually drew (reTerminal E1003)** — the IT8951 controller signals readiness over an HRDY line, and the driver's wait helper returned without telling its caller whether the line had ever gone ready, so every command in the display chain proceeded as if the controller had responded. In the field this produced a pathological failure: a single wake spent roughly **three minutes** retrying — dozens of consecutive three-second timeouts — kept the panel powered the whole time, drew nothing, and then reported the refresh as **successful**, so the cached image and the stored fingerprint were both updated for a picture that was never displayed. The wait helper now returns a result, with a short 250 ms timeout for ordinary commands and a longer 3 s allowance only at startup, and every step in the chain — register writes, device info, VCOM, temperature, power-on, frame upload, and the GC16 refresh — propagates failure and releases the SPI bus cleanly on the way out. Device info is validated as well, so a controller returning nonsense geometry or an invalid image-buffer address is caught at initialisation instead of corrupting an upload. A wedged panel is now detected in a fraction of a second rather than minutes, which on a battery device is the difference between a bad wake and a flat battery.

* **A failed panel gets one clean recovery attempt, and an honest result either way** — when the display chain fails, the driver performs a single bounded recovery: it releases both chip selects, tears the SPI bus down, power-cycles the panel rails, re-initialises the controller from scratch, and retries the upload and refresh exactly once. If that succeeds the wake proceeds normally. If it does not, the failure is logged plainly and reported as a failed draw — and, critically, the SD cache is **not** committed and the stored image fingerprint is **not** updated, so the next wake retries rather than believing it is already showing the right picture. The same rule now applies to the slot-carousel path: the cache is only written after the panel confirms it drew.

* **Stalled image downloads are abandoned instead of hanging the wake** — a download that opened successfully and then stopped producing data, such as a half-open connection or a server that accepted the request and went away, would wait indefinitely. The body reader now tracks when it last made progress and aborts after 15 seconds without new bytes, logging how far it got, and responses too short to be a valid image are rejected outright. Combined with the deferred NTP work and fast HRDY failure detection, every phase of a wake is now bounded.

* **Cache clearing no longer runs on the async network task** — the *Clear image cache* button deleted every cached file directly on the AsyncTCP callback, which is exactly where long blocking work must not happen: a small stack, no allowance for multi-second I/O, and on the reTerminal E1003 the SD card shares its SPI bus with the display, so the deletion could collide with a panel transaction. The request is now handed to the main loop and returns `202 Accepted` immediately (or `409` if a clear is already running), with the portal reporting the outcome. As a side benefit the SD work and the panel refresh now run on the same task and can no longer interleave on the shared bus. The delete loop also yields between files so a large cache cannot starve the watchdog.

* **Cached images are re-verified before they are trusted** — an entry read back from the SD cache has its CRC32 recomputed and its format re-validated before it is decoded. A cache file that has been truncated or corrupted is freed, evicted, and logged, and the frame falls back to a fresh download instead of drawing garbage or failing the wake.

* **Gallery countdown labels are shown again** — the *fresh for* and *expires in* labels on gallery cards had been left blank, so photos with a pending expiry or inside their freshness window gave no indication of how long they had left. Both are calculated again and rendered compactly (days and hours, hours and minutes, or minutes as appropriate), with no label shown for photos that have no deadline or whose deadline has already passed.

* **Smaller correctness fixes across the site and the frame** — an upload with a malformed lifetime value now returns a clear error instead of silently making the photo permanent, matching the behaviour the edit form already had. A wake whose cached image fails to draw and whose retry returns *keep* is reported as skipped rather than as a failed draw, so it no longer distorts reliability statistics. Image-processing failures return a fixed message to the caller with the detail logged server-side rather than echoing the raw exception. Archive import ignores files that no sidecar references. A configuration defining more than one user is now rejected at load with a clear error instead of silently hiding the site-administration surface. The legacy `tools/epaper-prep-gray16.py` cloud uploader is marked deprecated.

* **MCP core config tools — read and adjust device settings, notifications, volume, and timers from an AI assistant** — the board-agnostic MCP surface gains six tools (in `src/app/mcp_tools_config.cpp`) so an assistant can manage the same knobs a user sets in the web portal, not just pads. **Read tools**: `get_config` returns the current device settings (device name, network, MQTT/Home Assistant, power/transport, display + screen saver, audio) with secrets redacted to `<field>_set` booleans (passwords and tokens are never returned); `get_component_config` returns the saved JSON for one auxiliary feature — `timers`, `swipe`, `boot`, `button-defaults`, `hw-buttons`, or `mqtt-triggers` — reading it verbatim from the Storage facade (only components compiled into the board are accepted). **Control tools** (gated by the MCP control toggle): `notify` shows a message bubble on the screen (empty text dismisses it); `set_volume` sets (0–100) or adjusts (signed delta) the speaker volume; `timer_control` drives the three on-screen timers (`start`/`stop`/`toggle`/`pause`/`resume`/`reset`/`lap`/`set`/`adjust`, seconds for set/adjust); and `set_config` writes a curated, SAFE subset of device settings that apply **live without a reboot** — device name, backlight brightness, the `screen_saver_*` group, `mqtt_publish_interval_seconds`, `mqtt_publish_scope`, and `audio_volume`. WiFi/MQTT/HA credentials, operating mode, and security toggles are intentionally **not** writable over MCP (they can disconnect the transport carrying the request or lock the assistant out) and stay in the web portal. `notify`, `set_volume`, and `timer_control` build a `ButtonAction` and reuse the shared action-dispatch path; every control tool defers to the main loop via `mcp_control_dispatch()` (never touching `action_dispatch`, LVGL, or NVS on the web task). `set_config` parses its request on the web task into a PSRAM struct (the 192-byte screen-saver wake binding does not fit the 256-byte control slot) and applies it on the main loop, where screen-saver fields take effect live because the screen saver reads the same `DeviceConfig` instance. Tools self-gate on board capability (`notify`/`timer_control` need a display, `set_volume` needs audio). See [docs/mcp-guide.md](docs/mcp-guide.md).
* **MCP `set_component_config` + capability advertising** — the auxiliary-feature surface is now symmetric: `set_component_config` is the write counterpart of `get_component_config`, overwriting one feature's configuration (`timers`, `swipe`, `boot`, `button-defaults`, `hw-buttons`, `mqtt-triggers`) with a full-replacement `config` object. Unlike the portal's raw save paths, the write is **structurally validated** first — correct root/array shapes, action lists capped at `MAX_BUTTON_ACTIONS` with a non-empty `type` each, per-board count limits (`TIMER_COUNT`, `NUM_HW_BUTTONS`, `MAX_MQTT_TRIGGERS`), and non-wildcard MQTT trigger topics — and rejected with a reason if malformed, so an assistant cannot silently corrupt a feature. Read and write share one board-accurate component table (single source of truth), the serialized config is size-checked against each loader's cap, and the save is deferred to the main loop via `mcp_control_dispatch()` (PSRAM buffer, pointer+len, freed after `*_save_raw`). `set_component_config` is gated by the MCP control toggle. Separately, `get_capabilities` now emits a `device_config` section advertising `set_config`'s writable fields and the read/write component list, so an authoring client discovers the non-pad configuration surface from the manifest instead of probing each tool. `mqtt-triggers` read/write now gate on `MQTT_TRIGGERS_ENABLED` (matching the compiled feature) rather than `HAS_MQTT`. See [docs/mcp-guide.md](docs/mcp-guide.md).
* **MQTT-triggered actions** — a new device-level surface dispatches action lists when a matching MQTT message arrives, with no button, swipe, or screen involved. Each trigger pairs a topic with an optional exact-value filter and up to three sequential actions (the same action model as buttons, swipe gestures, boot, and timer-expire actions). When a subscribed topic receives a message, the firmware compares the payload against the filter (empty filter = match any payload) and, on a match, runs the trigger's actions. Triggers are edited from a new **MQTT Triggers** page in the web portal (`GET`/`POST /api/component/mqtt-triggers/config`) and persist to `/config/mqtt_triggers.json`; subscriptions are (re)established on every MQTT (re)connect. Wildcard topics (`#`, `+`) are rejected so each trigger targets one exact topic. The match runs inside the MQTT receive callback but only sets a per-trigger pending bit under a short spinlock — the actions themselves are dispatched from the main `loop()` via `action_list_dispatch()`, keeping the receive path non-blocking. The feature is compiled whenever `HAS_MQTT && (HAS_DISPLAY || HAS_BUTTON)`, so headless boards with a physical button (e.g. `esp32c3-withsensors`) can drive MQTT, BLE-HID, audio, and system actions, while e-paper / display-less + button-less boards (which keep MQTT but no action subsystem) exclude it entirely. Trigger capacity is `MAX_MQTT_TRIGGERS` (default 8, lowered to 3 on non-PSRAM boards); the config cache is allocated through the shared `config_psram_alloc()` helper (PSRAM-preferred with automatic SRAM fallback). New module `src/app/mqtt_triggers.{h,cpp}` and portal component `src/app/components/mqtt_triggers_component.cpp`. See [docs/web-portal-guide.md](docs/web-portal-guide.md) and [docs/dev/web-portal.md](docs/dev/web-portal.md).
* **Bar chart widget — multi-bar rendering, per-bar captions, and gauge-style scale options** — the bar chart widget is brought to parity with the multi-ring gauge, gaining several capabilities in this release. **Up to four bars** render in a single button: three optional **Bar 2 / 3 / 4 data binding** fields (`widget_data_binding_2`/`_3`/`_4`, reusing the framework-wide multi-binding plumbing) each add a bar when non-empty, every bar owns its **own track** (background, gridlines, and marker scoped to a single bar) with the tracks spread evenly across the full extent (columns when vertical, stacked rows when horizontal) at a fixed 6 px gap, and each bar has its own bindable fill color (**Bar 1–4 color**, `widget_bar_color`/`widget_bar_color_2`/`_3`/`_4`, defaulting to green/blue/purple/orange). **Bar width %** sets each bar's thickness *within its own column* (centered), so thin bars stay distributed instead of clustering. Each bar can show its **own caption** — four bindable **Bar 1–4 caption** fields (`widget_bar_label`/`_2`/`_3`/`_4`, 63 bytes each) resolve through the binding engine so a caption can mix static text with live data (e.g. `Solar [mqtt:home/solar;power;%.0f]W`), a literal `\n` becomes a line break for multi-line captions, and an optional **Caption size** field (`widget_bar_label_size`, 0 = auto) pins the caption strip to an exact pixel size (width in horizontal mode, height in vertical). Captions are colored to match their bar's fill, hidden when empty, re-resolve every tick, and render beneath each bar (vertical, centered) or in a strip to the left of each row (horizontal, right-aligned and vertically centered on the row). A shared scale drives three **gauge-style options**: **Zero-Centered** (`widget_bar_zero_centered`) anchors the fill at the scale's zero point so signed values grow in both directions (pair with a negative minimum, e.g. min `-5000` / max `5000`, for net power flow); **Gridlines** (`widget_bar_ticks`, 0–20) draw evenly spaced scale lines with a configurable width (`widget_bar_tick_width`) and bindable color (`widget_bar_tick_color`); and a **Target Marker** (`widget_bar_marker_value`, bindable) overlays a setpoint line with an optional shaded **Target Zone** band sized as a percentage of the range (`widget_bar_marker_zone_pct`), the marker width (`widget_bar_marker_width`) and marker/zone colors (`widget_bar_marker_color`, `widget_bar_marker_zone_color`) all configurable and bindable. Mirroring the multi-ring gauge's dual-ring mode, two **Dual Binding** toggles — **Dual Binding Bar 1 and 2** (`widget_bar_dual_binding_pair_1`) and **Dual Binding Bar 3 and 4** (`widget_bar_dual_binding_pair_2`) — collapse slots 1/2 and 3/4 into a single center-anchored bar when the partner slot is bound: the lower-index (near) bar owns the shared track and grows from the zero baseline toward the minimum while keeping its normal caption side (left horizontally, bottom vertically), and the higher-index (far) bar's fill is hosted inside the same track, grows toward the maximum, and shows its caption on the opposite end (right/top) — a `CAPTION1 ──‖████──‖ CAPTION2` layout horizontally or a stacked top/bottom layout vertically, with both halves scaling on the full `min..max` range (0 fixed at the baseline, so a symmetric look needs a negative minimum) while keeping their own bindable color and caption and leaving the target marker on the absolute scale. Bars that meet the zero baseline — both dual halves and single zero-centered bars — square off their baseline corners for a flat seam there while their outer ends keep the normal rounded corners. All new objects parent to their bar track so they clip to its bounds and reuse the widget's existing color-cache/change-detection pattern, so the render path is untouched when nothing changes. Single-bar, caption-less configurations render identically to before (every new field defaults to off/empty). Configured in the pad editor's **Bar Chart Settings**; see [docs/pad-editor-guide.md](docs/pad-editor-guide.md).
* **Sparkline line separation** — a new **Line Separation** setting (0–6 px, default 0 = off) in the Sparkline widget's Line Style section spreads multi-line charts vertically so lines with near-identical values no longer draw on top of each other. When enabled on a widget with more than one line, each line is nudged by a symmetric per-line offset (two lines fan out by ±offset, three lines by −offset / 0 / +offset) computed in `sparkline_rebuild_points()` and re-clamped into the chart; the current-value dot and min/max markers derive from the same pixel positions, so they shift with their line and stay connected. Reference lines and the Y-axis scale are unaffected (they map values independently). The offset trades a couple of pixels of value accuracy for guaranteed visibility, so it defaults off and existing pads render unchanged. Configured via `widget_sparkline_line_offset`. See [docs/pad-editor-guide.md](docs/pad-editor-guide.md).
* **Binding length guidance in the pad editor** — bindable fields with a shorter character limit (e.g. a sparkline line label or gauge min/max, capped at 63 bytes) now help the user when a binding does not fit instead of silently truncating it. When such a field is typed to its maximum length while it contains a `[` binding token, an inline amber hint appears on its own full-width line below the field pointing to **named pad bindings** as the fix: define the long `[mqtt:…]` topic once in the pad's **Bindings** list and reference the short `[pad:name]` alias in the constrained field. The hint is purely client-side (a delegated `input` listener scoped to the pad-edit dialog plus a re-scan when the dialog reopens, so stale hints clear), and the binding-help overlay's **Pad bindings** section gains a matching note explaining the same long-topic workaround.
* **Home Assistant Service button action** — a new `ha_service` button/swipe/boot/timer action calls any Home Assistant service over the REST API (`POST /api/services/<domain>/<service>`), letting a button toggle a light, run a scene, open a cover, etc. without a round-trip through MQTT. The HA base URL and a long-lived access token are configured once on the portal's **Home Assistant** page (`ha_url` / `ha_token` in `/api/config`, persisted to NVS); HTTPS targets are accepted (certificate not verified). In the action editor, the action takes an **Entity ID** (e.g. `light.living_room` — the service domain is derived from the text before the first `.`), a **Service** (e.g. `toggle`, `turn_on`), and an optional **Service Data (JSON)** object merged into the request body alongside `entity_id`. The call is dispatched from the UI task into a single-slot deferred queue and executed on the main `loop()` (via `action_dispatch_loop()`), so the HTTP request never blocks the LVGL render path; the new `ha_service.{h,cpp}` sender is compiled whenever `HAS_DISPLAY || HAS_BUTTON`. HA service calls are currently dispatched only on boards with a display (the `action_dispatch_loop()` drain is gated behind `HAS_DISPLAY`). The fields are stored literally (no binding-template resolution). See [docs/ha-integration-guide.md](docs/ha-integration-guide.md#service-actions-rest-api) and [docs/pad-editor-guide.md](docs/pad-editor-guide.md).

* **Hardware button actions** — physical GPIO buttons declared by a board can now run configurable tap and hold action lists, reusing the same action model as on-screen buttons, swipe gestures, and boot/timer actions. Boards opt in from `board_overrides.h` by setting `NUM_HW_BUTTONS` and declaring a `HW_BUTTON_DEFS[]` array of `{ pin, active_low, label }` entries (with an optional `HW_BUTTON_HOLD_MS` hold threshold, default 500 ms); the new interrupt-plus-debounce driver (`src/app/hw_buttons.{h,cpp}`) detects tap-vs-hold and dispatches up to three sequential actions per gesture through the shared `action_list_dispatch()`. Per-button tap/hold lists persist to `/config/hw_buttons.json` (`src/app/hw_button_config.{h,cpp}`) and are edited from a new **Hardware Buttons** page in the web portal (`GET`/`POST /api/component/hw-buttons/config`), which lists each declared button by label and GPIO. The feature is independent of `HAS_DISPLAY`, so headless boards (e.g. `esp32c3-withsensors`, which now exposes its GPIO9 button) can trigger MQTT, BLE-HID, audio, and system actions; display-only action types (screen, brightness, notify, timer) degrade to a logged no-op on screenless boards, and the portal page shows a note when the device has no display. The action subsystem (`action_dispatch`, `action_list`, `action_parse`, `action_registry`) and the filesystem mount (`storage_mount()`) are now compiled whenever `HAS_DISPLAY || HAS_BUTTON`.
* **E-paper wake-cycle telemetry breakdown** — the per-wake timing budget now decomposes the previously opaque `crc_to_draw_ms` into three observable sub-steps so long-term trends are visible without a serial console: `resolve_ms` (the carousel URL/API redirect round-trip), `fetch_ms` together with `image_source` (`cache` or `download`, distinguishing an SD-cache hit from a full body download and timing whichever ran), and `draw_ms` (framebuffer upload + GC16 panel refresh). The fields are staged by the active board driver as each phase completes, retained across deep sleep in RTC memory, published in the `<base>/epaper/state` MQTT payload (with four new Home Assistant discovery sensors — URL Resolve, Image Fetch, Panel Draw, and Image Source), and surfaced in the portal status JSON. A CRC-skip wake reports zeros for all three since no fetch or draw occurs. Diagnostic `LOGI` lines also report the URL-resolve time and the panel power-on overlap wait on the reterminal-e1003 driver, making the warm-wake critical path measurable at the device.

### Changed

* **Action-list config caches moved to PSRAM with automatic SRAM fallback** — the four action-list-based config caches (hardware buttons, boot actions, swipe actions, timers) previously lived in static internal SRAM. They are now heap-allocated through a new shared helper, `config_psram_alloc(size_t, const char*)` (`src/app/config_psram.{h,cpp}`), which prefers PSRAM (`heap_caps_calloc` with `MALLOC_CAP_SPIRAM | MALLOC_CAP_8BIT`) when `psramFound()` is true and transparently falls back to internal SRAM (`calloc`) on boards without PSRAM or if the PSRAM pool is exhausted. This reclaims roughly 9.3 KB of internal SRAM on the 13 PSRAM-capable boards while leaving behavior identical on non-PSRAM boards (`esp32c3-withsensors`, CYD-v2). Each module logs its placement once at boot under the `ConfigPSRAM` tag (e.g. "hw_buttons config: allocated 2528 bytes in PSRAM"), checks for allocation failure, and degrades gracefully — the getters return `nullptr` and every consumer (swipe dispatch, boot-action dispatch, and the hardware-buttons / boot-actions / swipe / timers portal pages) guards the dereference, so an out-of-memory board disables only the affected feature instead of crashing. The helper establishes a reusable pattern for future config caches. Affects `hw_button_config.cpp`, `boot_actions.cpp`, `swipe_config.cpp`, `timer_config.cpp`, and their consumers.
* **jc1060p470c UI scale lowered to the LARGE tier** — the 1024×600 Guition board now selects `UI_SCALE_LARGE` instead of `UI_SCALE_XLARGE` (in `src/boards/jc1060p470c/board_overrides.h`), a better fit for its panel size. Pad fonts shift from 18/24/36 to 14/24/32 (small/medium/large), the inter-button gap from 4 px to 3 px, and the icon height from 50% to 45% of button height. The other XLARGE board (`esp32-p4-lcd4b`, 720×720) is unchanged.
* **Gauge target zone drops the redundant edge ticks** — the gauge widget's target zone previously drew two boundary tick lines at the zone start and end *in addition to* the semi-transparent zone band and the center target tick, duplicating information the band's own edges already convey. The boundary ticks are removed so the gauge now matches the bar chart widget's cleaner model: a shaded zone band plus a single center marker tick at the target value. This is an internal rendering change only — no configuration, REST API, or web UI fields change (`widget_gauge_marker_tick_width`/`widget_gauge_marker_tick_color` still drive the center tick, and `widget_gauge_marker_zone_deg`/`widget_gauge_marker_zone_color` still define the band), so existing pads render unchanged apart from the missing edge ticks. Removing the per-ring `zone_ticks_lo`/`zone_ticks_hi` arrays also frees state and skips creating up to eight extra LVGL line objects per gauge. Affects `gauge_widget.cpp`.
* **Asset bundler treats `IS_*` device-class flags as one mutually-exclusive group** — `tools/minify-web-assets.sh` previously emitted `2^N` gzipped `#if`-guarded variants of each chunked web-asset bundle (one per combination of its unique chunk flags), treating the mutually-exclusive `IS_*` device-class flags as independent booleans and so generating combinations no board can ever match (e.g. `IS_SHUTTER_TESTER && IS_COFFEE_SCALE`). The variant generator now splits the flags into independent flags (`HAS_*`, still expanded `2^k`) and the device-class group (`IS_*`, expanded to `class_count + 1` exclusive branches — one per class plus a "none" branch), collapsing `portal.js` from 32 variants to 16 and `portal_all.css` from 8 to 4 while keeping per-board output byte-identical. Each positive class branch negates its siblings and the "none" branch negates all, so the emitted branches are provably exclusive and exhaustive (a misconfigured two-class board would match zero branches → a loud link error, never a silent duplicate). The old "max 5 unique flags" stopgap cap is replaced by a 32-variant backstop that only independent flags can drive toward, so adding further device classes no longer trips it. A new host guard `tests/test_asset_variant_matrix.sh` (wired into `tests/run_tests.sh`) brute-forces the full flag truth-table against the real generator to assert exclusivity and exhaustiveness without building any board. Resolves [#31](https://github.com/jantielens/esp32-macropad/issues/31).
* **Device-class action types expose a single `value_field` accessor** — the per-type `ActionTypeDef` binding hooks (`resolve_bindings`, `has_binding`, `substitute_step`) — each of which only ever targeted the device-class payload's single `value` field — are collapsed into one `value_field(ButtonAction&, size_t*)` accessor. Shared firmware in `action_registry.cpp` now implements binding resolution, the `[`-token scan, and `{step}` substitution generically against the returned field, so a new action type only declares where its bindable value lives. This removes duplicated boilerplate across the darkroom-timer, coffee-scale, and shutter-tester action types with no change to runtime behavior.

### Fixed

* **Sparkline current-value labels no longer slightly overlap** — the per-line current-value labels stacked in the right margin spaced themselves using the font's nominal line height (`+2 px`), which ignores label padding and the real glyph extent, so adjacent labels could touch or overlap by a pixel or two. The collision pass now measures the tallest rendered label box (`lv_obj_update_layout` + `lv_obj_get_height`, the same pattern already used for the min/max labels) and adds an explicit 3 px gap, so spacing matches what is actually drawn. The overflow path was also reworked: when the stack fits, it is shifted as a single block (preserving spacing) rather than clamping each label independently — the old per-label clamp could collapse two or three labels onto the same row when the chart was too short; when the stack genuinely cannot fit, labels are now distributed evenly across the available height instead of stacking. Affects `sparkline_redraw()` in `src/app/widgets/sparkline_widget.cpp`.
* **Sparkline current-value dot no longer detaches from a line that hugs the chart edge** — the per-line current-value dot sits at the line's rightmost vertex, but the chart container (`chart_area` in `src/app/widgets/sparkline_widget.cpp`) inherited a non-zero corner radius from the theme and ran with `clip_corner` enabled. When a data line ran flat along the top or bottom edge (e.g. a value pinned at its auto-scaled max), the rounded top-right corner wedge clipped the line's end *inside* the container, while the dot — a tile child that is not corner-clipped — overhung past the edge, leaving a visible gap. Lines crossing mid-height were unaffected. The container's radius is now forced to 0, so edge-hugging lines reach the corner and stay connected to the dot; rectangular child-clipping still confines lines to the tile.
* **`[pad:name]` bindings now work in Sparkline (and other stream) data bindings** — a named pad binding (e.g. `[pad:grid]`) worked in button labels but silently produced an empty line when used as a Sparkline **Data Binding**. History-based widgets attach to their data through a string-keyed stream lookup: `data_stream_rebuild()` registered each stream under the *expanded* template (`[pad:grid]` → `[mqtt:...]`), while the widget looked its stream up with the *raw* `[pad:grid]`, so the two keys never matched (`data_stream_find()` returned `DATA_STREAM_INVALID`). `PadScreen::buildTiles()` now expands `[pad:]` tokens in each widget's `data_binding[]` (via `pad_binding_expand()`) before `createUI()` runs, so both sides key off the same expanded string. Labels were unaffected because they resolve `[pad:]` live through the binding scheme rather than by stream key.
* **Gauge track/needle/tick color fields no longer accept silently-truncated input** — these three bindable color inputs in the pad editor advertised `maxlength="191"` but their firmware buffers are only 64 bytes (`CONFIG_BINDABLE_SHORT_LEN`), so a long binding entered in the portal was accepted by the browser then truncated on save. The frontend `maxlength` is lowered to 63 to match the backend (consistent with the gauge marker color fields), making the limit honest. For long MQTT-topic bindings that exceed 63 characters, define a `[pad:name]` named binding (191-char value) and reference it instead.
* **Washed-out colors after multi-hour screensaver sleep on jc1060p470c (active LC de-bias)** — on cheap IPS MIPI-DSI panels (JD9165 + HKC), holding the panel in hardware reset all night (`DISPLAY_HARD_RESET_ON_SLEEP`) still left the LC cells washed out for a few minutes after wake: power-down alone does not cancel the DC bias that accumulates in the cells, it only lets it relax slowly. The periodic sleep-refresh hook (`MipiDsiDriver::displayRefreshSleep()`, previously a no-op in hard-reset mode) now performs an active de-bias: it briefly powers the panel back up and drives `DISPLAY_DEBIAS_CYCLES` (default 3) full-frame white↔black inversion cycles — `DISPLAY_DEBIAS_HOLD_MS` (default 80 ms) per half-cycle — to drive opposite-polarity charge through the LC and cancel the accumulated bias, then re-asserts reset to power the IC back down. The backlight stays at 0 throughout (the screensaver is fully asleep), so the de-bias is invisible. The refresh leaves the panel in the same resting state as before (RST low, framebuffers black), so the wake path is unchanged: clean fade from black into the proper screen at the same ~180–230 ms latency. Two new board-overridable knobs (`DISPLAY_DEBIAS_CYCLES`, `DISPLAY_DEBIAS_HOLD_MS`) tune the de-bias strength; the de-bias cadence reuses the existing `SCREENSAVER_SLEEP_REFRESH_MS` (default 15 min). Affects all P4 MIPI-DSI boards that enable `DISPLAY_HARD_RESET_ON_SLEEP`. See [docs/compile-time-flags.md](docs/compile-time-flags.md).
* **Morning flicker after overnight screensaver sleep on jc1060p470c (keep panel powered)** — distinct from the washed-out-colors issue above, the JD9165 + HKC IPS combo also flickered for a couple of minutes after waking from a multi-hour sleep, then self-stabilized (a full power cycle fixed it instantly). The de-bias refresh alone did not resolve it: the hard-reset wake path only toggles RST and replays the DCS init, but never re-initializes the MIPI-DSI PHY/LDO/DPI peripheral the way cold boot does, so a full night of power-down left a marginal VCOM/MIPI-lock state that the lightweight wake could not recover. jc1060p470c now defaults to a new `DISPLAY_KEEP_PANEL_AWAKE_ON_SLEEP` mode instead: the panel stays in normal Display On, scanning an all-black framebuffer (the opaque sleep overlay keeps LVGL rendering black, so the frame is DC-balanced and no image retention or Sleep-In bias builds up) with only the backlight faded to 0 — sleep looks identical to the user. No DCS Sleep In, no RST toggle, no power-cycling, so wake is a clean backlight fade with no flicker and no washout. Trades higher idle power (panel + DSI stay active) for a power-cycle-free wake, acceptable on a mains-powered device. The new flag takes precedence over `DISPLAY_HARD_RESET_ON_SLEEP` in the `MipiDsiDriver` sleep/wake/refresh paths (the two are mutually exclusive); the de-bias and hard-reset behavior remain available for other boards. See [docs/compile-time-flags.md](docs/compile-time-flags.md).
* **Icon store cache is now thread-safe** — the in-memory icon cache (`g_entries`/`g_count`/`g_capacity` in `src/app/icon_store.cpp`) was read by the LVGL render task (`icon_store_lookup()` during tile building) while the async web server task could mutate it (`icon_store_install()` → `cache_entry_buf()`, `icon_store_delete_page_icons()`, `icon_store_enumerate_cache()`). An icon upload that triggered the cache's `realloc` growth — or a page-delete that compacted entries — could invalidate the array pointer mid-read on the render task, risking a crash or corrupted draw. A FreeRTOS mutex now guards every in-memory table access; the critical sections cover only the table touches, leaving PNG decode and `Storage` file I/O outside the lock so the render path is never stalled on disk or decode work. Resolves [#4](https://github.com/jantielens/esp32-macropad/issues/4).
* **E-paper NTP resync no longer taxes every wake** — re-syncing NTP on every duty-cycle wake (added in 1.20.0) paid lwIP's randomized SNTP startup delay (~3–5 s) on the critical path each cycle, racing the HTTPS image download and inflating the wake-to-visible time. The firmware now skips the network sync when the RTC clock is already valid and the last successful sync is under one hour old (matching ESP-IDF's default SNTP update cadence), fetching only on cold boot or when a resync is due — and when it does fetch, it blocks on the SNTP sync-notification callback before starting the download so the two never contend on the WiFi stack. This keeps warm-wake refreshes fast while still bounding RTC drift, and the `ntp_sync_ms` telemetry now reports 0 on skipped wakes and the true cost on resync wakes.

## [1.20.0] - 2026-06-05

This release grows the **e-paper device class** — introduced in 1.17.0 with the single Inkplate 5V2 board — into a proper multi-board class. Two new panels join it: the **Seeed reTerminal E1003** (10.3" 1404×1872 IT8951 on an ESP32-S3) and the **Soldered Inkplate 6FLICK** (6.0" 1024×758 Inkplate 3-bit on an ESP32 classic). Alongside the boards, this release lands the shared image-transport plumbing that keeps the battery-powered wake path fast on all three: a compressed **G16Z** transport that cuts WiFi bytes by ~2–3×, an optional **SD blob cache** that skips the re-download entirely on a cache hit, a self-hosted HTTPS image downloader (replacing InkplateLibrary's crashing one), and a wake-to-visible path that overlaps panel power-up with the WiFi association.

Wired into the build via `config.sh` (`Inkplate_Boards:esp32:Inkplate6Flick`), GPIO36 wake button, and the shared e-paper duty-cycle runtime. Both Inkplate boards now download images themselves through a shared `epaper_http_download` helper (`HTTPClient` + `WiFiClientSecure::setInsecure()`, cross-host redirect following) and pick the decoder by sniffing the JPEG/PNG/BMP magic bytes, replacing InkplateLibrary's HTTPS downloader, which crashed on `https://` hosts. The bundled [`tools/photoframe-site`](tools/photoframe-site/README.md) reference server now emits baseline 3-component (RGB) JPEG so the Inkplate's bundled TJpgDec decoder accepts it (single-component grayscale JPEGs were rejected); a per-device config entry just selects JPEG output at 1024×758. See [docs/epaper-guide.md](docs/epaper-guide.md).
* **Seeed reTerminal E1003 e-paper board (`reterminal-e1003`)** — a second `epaper` device-class target: a 10.3" 1404×1872 16-level grayscale panel driven by an IT8951 controller on an ESP32-S3 (XIAO form factor, 32 MB flash + 8 MB OPI PSRAM). The driver is self-contained (raw IT8951 HSPI sequences plus a 4 bpp PSRAM framebuffer wrapped in Adafruit_GFX) and draws dashboard images at the panel's native resolution with no on-device scaling, prioritizing the battery-powered refresh path. It accepts a server-supplied **G16P** payload (pre-dithered 4 bpp packed nibbles, copied straight into the framebuffer) as the fast path, and falls back to decoding a baseline JPEG with JPEGDEC and Floyd–Steinberg dithering on-device. Shares the existing e-paper duty-cycle runtime (scheduled wake, CRC-skip refresh, status overlay, deep sleep) and Refresh-button wake. The portal VCOM page is hidden on this board (`HAS_EPAPER_VCOM=false`, since the IT8951 sets VCOM internally). Seeed_GxEPD2 is git-installed by `setup.sh`; `Adafruit GFX Library` and `JPEGDEC` are added as registry dependencies. See [docs/epaper-guide.md](docs/epaper-guide.md).

#### Shared e-paper image transport

* **SD image cache for e-paper boards** — an optional downloaded-blob cache for e-paper device-class boards that expose a microSD slot on the panel's shared SPI bus, gated by the `EPAPER_SD_CS_PIN` compile-time flag (enabled on `reterminal-e1003`, compiled out on `inkplate5v2`). On a cache hit the firmware reads the cached transport blob (G16Z, or G16P when the server sent an uncompressed frame) from SD and skips the HTTP body download; on a miss the blob is written back to the card on the awake tail so the write stays out of the wake-to-visible path. A **Cache images on SD** portal toggle (NVS key `ep_sd_en`, default off) and a **Clear SD cache** action control it; the toggle is shown only on boards that report the capability. See [docs/epaper-guide.md](docs/epaper-guide.md#sd-image-cache).
* **Compressed G16Z image transport for e-paper boards** — the e-paper firmware and the bundled [`tools/photoframe-site`](tools/photoframe-site/README.md) reference server support an optional raw-DEFLATE `G16Z` wrapper around the G16P framebuffer (`G16Z` magic + raw DEFLATE of the full G16P bytes). The server compresses each upload when it shrinks the payload, so the device pulls ~0.3–0.5× the bytes off WiFi and inflates into a PSRAM buffer with the ROM's malloc-free tinfl before rendering the reconstructed G16P. Raw (uncompressed) G16P blobs are still accepted. On boards with the SD image cache, the **compressed** transport blob is written back, so a later cache hit skips the re-download and reads only ~0.4 MB off the shared HSPI bus (vs ~1.3 MB for a full G16P) before re-inflating in PSRAM. Added a [`tools/photoframe-site/README.md`](tools/photoframe-site/README.md) documenting the server as a sample reference implementation, and clarified [`tools/panel-calibration/README.md`](tools/panel-calibration/README.md) as one-shot bring-up tooling.

### Changed

* **Faster e-paper wake-to-visible path** — the duty-cycle hook now overlaps the slow panel power-up with the WiFi association instead of running them back to back. On boards whose battery sense is independent of the panel rails (E1003), the cell voltage is read and the low-battery gate runs up front, then panel init runs on a background PSRAM-stack task concurrently with the WiFi connect (two independent buses), shaving roughly the shorter of the two off the critical path. Boards whose battery sense is gated behind panel init (Inkplate) keep the original ordering with no behavior change. The hook also no longer sleeps and re-powers the panel between the healthy-battery gate and the draw, so the ~1.6 s IT8951 power-on is paid once per wake rather than twice. New `epaper_driver_begin_async()` / `epaper_driver_begin_join()` / `epaper_driver_battery_ready_before_begin()` HAL entry points back the overlap.
* **Cached-AP RSSI floor is now configurable** — the WiFi reconnect path's signal-strength floor for trusting a cached access point is exposed as the `WIFI_CACHED_RSSI_FLOOR_DBM` compile-time flag (default `-78`) instead of a hard-coded constant, so boards with marginal antennas can tune it via `board_overrides.h`. See [docs/compile-time-flags.md](docs/compile-time-flags.md).
* **WAKE button overrides the e-paper schedule** — a short press of the WAKE button now refreshes the image even when the current local hour is disabled in the hourly schedule. Previously a button wake during a disabled hour went straight back to sleep without drawing; now the button wins and forces the refresh, then normal scheduled sleeping resumes on the next timer wake. Timer wakes still honor the disabled hours.

## [1.16.0] - 2026-05-24

### Added

- **Hard-reset screensaver sleep for cheap IPS MIPI-DSI panels (`DISPLAY_HARD_RESET_ON_SLEEP`)** — new compile-time flag (default `false`) that holds the panel hardware reset pin LOW for the duration of screensaver sleep so the panel IC fully powers down its internal regulators. Required on boards where DCS Sleep In + framebuffer blanking alone does not de-bias the TFT cells, leading to washed-out colors after multi-hour idle (observed on jc1060p470c: JD9165 + HKC IPS panel). Wake re-runs the full vendor init sequence; latency grows from ~120 ms to ~180-230 ms. `DisplayDriver::needsTwoPhaseWake()` lets the screensaver skip the 120 ms DCS gap and second lock acquisition for single-phase wake paths. Enabled by default on jc1060p470c.
- **Periodic sleep-refresh hook (`SCREENSAVER_SLEEP_REFRESH_MS`, `DisplayDriver::displayRefreshSleep()`)** — new compile-time flag (default 15 min, 0 disables) and virtual driver method called by the screensaver while fully asleep, so drivers can re-blank framebuffers or otherwise scrub residual state during long idle. `MipiDsiDriver` re-blanks both DPI framebuffers (no-op when the hard-reset path is active, since the panel IC is already unpowered).
- **BTHome v2 BLE telemetry transport** — duty-cycle boards can now advertise sensor readings as unencrypted BTHome v2 BLE advertisements instead of (or in addition to) MQTT, removing the Wi-Fi + broker dependency on the device side. Receivers like Home Assistant's built-in Bluetooth integration decode the advertisements directly. A new compile-time flag `HAS_BLE` (default `false`) controls inclusion of the new `ble_telemetry` module, which exposes `ble_telemetry_init()`, `ble_telemetry_set_{u8,u16,s16}(object_id, value)`, and `ble_telemetry_advertise_burst(count, interval_ms)`. Sensor adapters buffer their latest reading from their `update()` path; the duty-cycle orchestrator then emits a configurable advertising burst and deep-sleeps. Two new persistent settings are exposed (gated on `HAS_BLE`): `ble_burst_count` (default 3) and `ble_adv_interval_ms` (default 100). The Home → Operating Mode card gains a "Duty-Cycle (BLE)" radio option (hidden on builds without `HAS_BLE`) with inline burst-count / advertising-interval controls. New reference board `esp32c3-withsensors` (ESP32-C3 Super Mini + dummy_sensor) ships with `HAS_BLE=true`, `HAS_BLE_HID=false`, and `HAS_DISPLAY=false`, advertising its dummy value as BTHome temperature (object id 0x02, scaled by 100).
- **Compile-time capability map in `/api/config`** — the device-config endpoint now includes a `caps` object (`ble`, `mqtt`, `display`, `ble_hid`) reflecting the compile-time `HAS_*` flags. The portal caches this in `window.__device_caps` and uses it to hide UI controls for unsupported features (currently the BLE operating-mode radio).
- **First-boot setup wizard** — when the device boots into AP mode without WiFi configured (first boot or after factory reset), the portal now lands the user directly on a single-card onboarding fragment instead of the generic welcome page. The wizard collects everything needed to get on the network in one form: WiFi SSID + password (required), friendly name (with live mDNS hostname preview), and two checkbox-gated optional sections — "Require login for the portal" (basic auth username/password) and "Use a static IP address" (IP/subnet/gateway/DNS). MQTT, BLE, and operating mode are intentionally left out — they belong to post-onboarding configuration. The wizard submits to the existing `/api/config` endpoint and reboots immediately. Implementation: new `setup` component (`src/app/components/setup_component.cpp` + `src/app/web/setup.fragment.html`), gated to be visible only in AP mode and hides the other Device-category items while active so it is the single hand-off path. `GET /api/portal/nav` now emits an `ap_mode: true` flag and a top-level `primary: { fragment: "setup", category: "device" }` hint, and `portal_nav.js` prefers `primary.fragment` over any stale URL hash when `ap_mode` is true so the wizard wins even if the browser re-opens with a leftover `#welcome` hash.
- **SD card storage option** — boards can now route all persistent file I/O (pad configs, icons, sounds, boot/swipe/timer/button-default configs, indexed stores) to a MicroSD card via SDMMC instead of the internal LittleFS partition. Enabled per board with `HAS_SD_CARD true` + `USE_SD_STORAGE true` in `board_overrides.h`. Primary motivation: on MIPI-DSI / RGB panels, internal-flash cache disables during writes starve the framebuffer DMA and cause visible flicker; moving the working set to SD eliminates the flicker. A new header-only `Storage` facade (`src/app/storage.h`) resolves to `LittleFS` or `SD_MMC` at compile time — both extend `fs::FS` so call sites are identical. When SD storage is enabled, the device halts at boot with a `SD CARD MISSING` splash if the card is missing or unreadable (no runtime fallback). A separate `SD_PROBE_ON_BOOT` flag runs a diagnostic mount + directory listing + write/read round-trip for new-board bring-up. Storage usage published to Home Assistant reports SD card capacity (GB) instead of the partition size (MB). Hardcoded for SDMMC Slot 0 IOMUX, 4-bit @ 40 MHz with the jc4880p433 pinout (CLK=43, CMD=44, D0=39, D1=40, D2=41, D3=42, POWER=45 active-LOW, LDO channel 4); other board pinouts require editing `sd_storage.cpp`. No board enables the flag in this release — the infrastructure is in place for future variants.
- **New `ota_2mb` partition scheme for 4 MB-flash headless boards** — `partitions/partitions_ota_2mb.csv` drops the 128 KB SPIFFS slot (unused on `HAS_DISPLAY=false` builds — `pad_config`, `fs_indexed_store`, and `web_portal_fs_store` are all `HAS_DISPLAY`-gated) and grows each OTA app slot from `0x1E0000` to `0x1F0000` (+64 KB headroom per slot). `esp32c3-withsensors` now ships with `PartitionScheme=ota_2mb` in `config.sh`. Auto-installed via `tools/install-custom-partitions.sh`.

- **Renamed `power_mode` config field to `operating_mode` (breaking, no migration)** — the NVS key `pwr_mode` was renamed to `op_mode`, the C++ field `DeviceConfig::power_mode` to `DeviceConfig::operating_mode`, the macro `CONFIG_POWER_MODE_MAX_LEN` to `CONFIG_OPERATING_MODE_MAX_LEN` (16 → 20 chars), and the `/api/config` JSON field `power_mode` to `operating_mode`. Devices flashed from a previous build fall back to the `always_on` default after the rename — the operating mode must be re-selected once in the portal.

Changes: (1) toast container moved from `bottom-0 end-0` to top-right, anchored just below the page header via `top: calc(var(--portal-header-height-desktop, 120px) + 12px)` so it never overlaps the pad-editor toolbar; (2) removed redundant toasts where the result is already visible: "Button moved" (drag), "Button pasted" (cell updates visibly), "Device config exported" (browser shows the download), "Import complete — rebooting device…" (the reboot overlay already says this), and the "Selected: file.bin (N KB)" info toast on the OTA file picker (the `<input>` already shows the filename); (3) recolored progress-style toasts from `success` (green) to `info` (grey): "Exporting device config…", "Importing device config…", and "Showing &lt;screen&gt; on device"; (4) trimmed "Configuration saved successfully!" to "Configuration saved" for consistency with the other save toasts.

### Fixed

- **MIPI-DSI screensaver leaving panel under continuous scanout (image retention mitigation)** — `MipiDsiDriver::displaySleep()` previously only sent the DCS Display Off (`0x28`) + Sleep In (`0x10`) commands. The ESP-IDF DPI peripheral keeps scanning the framebuffer over the MIPI lanes at 60 Hz for the entire sleep period regardless of DCS state, so on long idle stretches (e.g. overnight) the panel's source drivers were fed the same identical image for hours — a textbook cause of IPS image persistence (washed-out colors and faint ghosting that fade over several minutes after wake). `displaySleep()` now zeroes both DPI framebuffers (with `esp_cache_msync` PSRAM cache flush) before the DCS power-down, so the DPI peripheral's ongoing scanout reads all-black for the entire sleep period. (Gating the DPI peripheral itself via `esp_lcd_panel_disp_on_off()` was attempted but is not implemented for DPI panels in our ESP-IDF version.) Applies to all three P4 MIPI-DSI boards (esp32-p4-lcd4b, jc4880p433, jc1060p470c); other drivers (Arduino_GFX_ST77916, TFT_eSPI) already had their own sleep overrides and are unchanged.
- **Health widget broken on Pad Editor and Sensor Data fragments** — the floating health bubble's expanded overlay (`{{HEALTH_WIDGET}}`) is already rendered once by the shell (`shell.html`), but `pad-editor.fragment.html` and `sensor-data.fragment.html` also included the placeholder. When either fragment loaded, the DOM ended up with two `#health-expanded` containers, two `#health-close` buttons, and two sets of sparkline canvases sharing the same IDs. `getElementById('health-expanded')` returned the shell's copy (correct), but the duplicate `position: fixed; z-index: 1050` overlay div from the fragment stacked on top of the shell's, intercepting clicks on the close button; the duplicate sparkline canvases (also with shared IDs) confused the sparkline updater so the visible chart never refreshed. Removed `{{HEALTH_WIDGET}}` from both fragments — the shell provides the only copy.
- **Stack canary crash in WiFi gateway-ping task** — the gateway liveness probe (`wifi_ping_start` in `wifi_manager.cpp`, sends one ICMP echo to the router every `WIFI_PING_INTERVAL_MS` to detect "WiFi reports connected but link is dead") created its FreeRTOS task with a 2 KB stack. With lwIP's ICMP send/recv path plus the on-end callback, 2 KB was marginal: when a low-priority ISR fired while the ping task was at peak stack depth the canary watchpoint tripped and the device panicked (`Guru Meditation Error: Stack canary watchpoint triggered (ping)`, PC in `_xt_lowint1`, backtrace corrupted). Reproduced on jc3636w518 after ~90 min of uptime. Bumped `cfg.task_stack_size` to 4096 for comfortable headroom; callbacks remain flag-write-only so the increase is the only change needed.
- **AP-mode first-boot save no longer rejected by basic-auth guard** — the `/api/config` POST handler used to block any payload containing `basic_auth_*` fields whenever the device was in AP mode, to prevent an attacker in a fallback-AP session from locking out the legitimate owner. That guard fired on legitimate first-boot saves too, returning `403 "Basic Auth settings cannot be changed in AP mode"` and surfacing as an "Error saving: failed to save configuration" toast in the wizard. The guard now exempts the true first-boot case (current stored `wifi_ssid` is empty) so the wizard can enable auth during onboarding; the fallback-AP-mode protection is unchanged for any session after WiFi has ever been configured.
- **Captive-portal redirect loop on Android** — `handleRoot` previously issued an HTTP 302 to `/#setup` in AP mode. Android's captive-portal detector follows the redirect under its own probe hostname (`connectivitycheck.gstatic.com/generate_204`), receives an HTML body instead of a 204, and concludes the network still requires sign-in — causing a refresh loop. The root handler now always serves the SPA shell with HTTP 200; landing-fragment selection happens client-side via the nav API's `primary.fragment` field, which is what mobile captive-portal browsers expect.
- **Save button hidden under mobile browser URL bar** — the portal layout used `100vh` for its main flex container. On Android Chrome/Edge, `100vh` is computed against the largest viewport (URL bar collapsed), so when the URL bar was visible the content pane's bottom — including the save bar — sat behind the browser chrome. The layout now uses `100dvh` (dynamic viewport height) with a `100vh` fallback for older browsers, so the save bar stays inside the visible viewport regardless of URL-bar state.
- **Pull-to-refresh fires on portal scroll** (regular browsers only) — added `overscroll-behavior-y: contain` on `body` and `.content-pane` to stop the internal scroller from bubbling a top-of-page event up to Chrome/Edge's built-in pull-to-refresh. The same gesture in Android's captive-portal popup (`com.android.captiveportallogin`) is handled by a system-level `SwipeRefreshLayout` wrapping the WebView and cannot be suppressed from CSS — open the portal in a regular browser tab for the wizard if PTR becomes disruptive.
- **Portal components silently absent from registry** — `src/app/components/setup_component.cpp` was added without a matching `#include` in `src/app/portal_components.cpp`. Arduino's build system only compiles `.cpp` files in the sketch root, so the file compiled successfully (via the IDE indexer) but its `REGISTER_COMPONENT()` static initializer never ran — the component was silently absent from `/api/portal/nav`. Added the include and documented the aggregation pattern in both `.github/copilot-instructions.md` and the new "Component Registration" section of `.github/instructions/web-portal.instructions.md` (also extended the latter's `applyTo` glob to cover `components/*_component.cpp` and `portal_components.cpp`) so future component additions surface the requirement automatically.
- **Infrequent screen flicker with image / MJPEG widgets on ESP32-P4 MIPI-DSI boards** — several PSRAM-bandwidth and synchronization fixes addressing flicker observed when pad buttons display image-URL backgrounds or MJPEG streams on esp32-p4-lcd4b, jc4880p433, and jc1060p470c:
  - **Image fetch zero-copy hand-off** — each image slot now owns a third PSRAM buffer (`lvgl_buf`) that LVGL points to directly. `image_fetch_get_frame()` atomically swaps `front_buf ↔ lvgl_buf` under the slot mutex instead of the previous LVGL-side `realloc` + `memcpy` on every new frame. Removes the per-frame PSRAM copy from the LVGL task. The retired `owned_pixels` / `owned_pixels_size` fields on `ButtonTile` are removed; `PadScreen::pollImageFrames()` now writes the new pointer directly into `lv_image_dsc_t::data` and calls `lv_obj_invalidate()`.
  - **Fetch task pinned to PRO_CPU (core 0)** — the image fetch FreeRTOS task previously ran with `tskNO_AFFINITY` and could land on core 1 alongside the LVGL render task, causing cache-line contention with LVGL during JPEG decode and PPA scaling. Pinning to core 0 isolates it from LVGL.
  - **Removed `heap_caps_check_integrity_all(true)` from fetch hot path** — three diagnostic calls per fetch cycle were stalling the task for several milliseconds when the heap grew large.
  - **MJPEG poll throttle respects `interval_ms`** — the round-robin slot scan no longer short-circuits to streaming slots when a non-zero interval is configured; post-decode yield bumped from 5 ms to 10 ms while streaming. Prevents one MJPEG stream from starving other slots and the LVGL task.
  - **Defer image-frame hand-off while DMA2D flush is active** — new `displayDriverIsFlushBusy()` accessor (backed by `g_displayFlushBusy` set/cleared by the MIPI-DSI driver around `esp_lcd_panel_draw_bitmap` / `onColorTransDone` ISR). `pollImageFrames()` early-returns while the flag is set so `lv_image_set_src` + `lv_obj_invalidate` don't add PSRAM bandwidth pressure or dirty regions that compete with the in-flight scanout. The frame stays buffered in `image_fetch` and is picked up next LVGL tick.

- **DMA-internal heap visibility (ESP-Hosted SDIO crash diagnostics)** — `/api/health` now reports `heap_dma_internal_free`, `heap_dma_internal_min`, and `heap_dma_internal_largest` (bytes from `MALLOC_CAP_DMA | MALLOC_CAP_INTERNAL`). This is the pool that backs AsyncTCP / LWIP TX pbufs on ESP32-P4 with the ESP-Hosted SDIO co-processor, and the specific signal that precedes `transport_drv_sta_tx` / `copy_buff` NULL asserts under portal load. The broader `heap_internal_free` can look healthy while this subset is exhausted, so it needs its own metric. The 200 ms health-window sampler also emits a throttled `LOGW("HealthHist", "DMA-internal heap low: ...")` (rate-limited to 5 s, threshold 8 KB) so post-crash serial logs contain a proximate watermark marker.
- **Portal HTTP request reduction (ESP-Hosted SDIO DMA pressure)** — cut the number of concurrent HTTP responses during a portal boot to reduce DMA-internal SRAM fragmentation that was causing `transport_drv_sta_tx` / `copy_buff` NULL asserts on ESP32-P4 boards with the ESP-Hosted SDIO co-processor. Changes: (1) the frontend wraps `window.fetch` with a 2-deep concurrency cap; (2) a new `getDeviceInfo()` helper caches `/api/info` for the page session (5+ duplicate calls → 1) and coalesces concurrent first-time fetches, and `fetchHealthOnce()` in `portal_health.js` exposes the widget's most recent `/api/health` snapshot to the welcome and version-info fragments so they no longer issue their own `/api/health` requests at boot; (3) `bootstrap.min.css` + `portal-custom.css` are concatenated into a single `/portal-all.css` bundle (1 request instead of 2, ~1.5 KB smaller via shared gzip dictionary); (4) `<link rel="icon" href="data:,">` in `shell.html` suppresses the browser's automatic `/favicon.ico` lookup; (5) the legacy `GET /api/mode` endpoint and matching JS `loadMode()` were removed — portal mode is now derived from the new `ap_active` field on `/api/info`; (6) the gzipped PROGMEM asset handler in `web_portal_pages.cpp` (shell HTML, `portal-all.css`, `portal.js`, fragments) now streams via a length-aware chunked `AwsResponseFiller` callback (`HTTP_STREAM_CHUNK_SIZE = 4 KB`) instead of `beginResponse_P()`, so AsyncTCP paces segments as LWIP TX buffers free up rather than dumping the full ~90 KB CSS+JS payload into the DMA-internal pbuf pool when the browser fetches both in parallel. A fresh portal load now issues `/ + /portal-all.css + /portal.js + /api/info + /api/health + /api/portal/nav + /api/section/welcome` (plus the periodic health poll) with at most 2 concurrent in-flight requests. Documented in `docs/dev/web-portal.md` under [Concurrent Request Throttling](docs/dev/web-portal.md#concurrent-request-throttling).
- **Atomic rename idempotency on SD/FAT and LittleFS** — `FsIndexedStore::_atomic_write*()` now removes any pre-existing destination file before calling `rename()`. Both LittleFS and SD/FAT `rename()` fail if the destination already exists, which broke manifest writes (`_index.json`) on SD-backed boards whenever a prior manifest was present. The temp-file-then-rename crash-safety guarantee is unchanged; the extra `remove()` only fires when a stale destination is present.
- **WiFi TX buffer exhaustion prevention** — prevent `transport_drv_sta_tx` assert crashes on ESP32-P4 (ESP-Hosted SDIO) caused by outbound traffic bursts. Large file downloads (session data, FsIndexedStore documents) now stream through a chunked `AwsResponseFiller` callback with a 4 KB cap (`HTTP_STREAM_CHUNK_SIZE`) instead of `request->send(LittleFS, ...)`, letting the async TCP event loop yield between chunks. MQTT post-connect burst (HA discovery, subscribes, state publishes) is paced with `delay(1)` yield points between handler groups in `onConnected()` and between batches of discovery publishes in `ha_discovery_publish_health()`. Total added latency is ~10 ms — imperceptible on connect time. Applies to all boards (non-P4 boards also benefit from reduced lwIP buffer pressure).
- **BTHome v2 advertisements not discovered by Home Assistant** — two issues prevented HA from picking up the new `esp32c3-withsensors` reference build over BLE: (1) the 22-character device name consumed 24 of the 31-byte legacy-advertisement budget, leaving only 4 bytes for the 8-byte BTHome service-data block — the controller silently dropped the service data, so the advertisement on air carried only Flags + Name. The name is now moved to the scan response so the primary advertisement carries Flags + BTHome service data exclusively. (2) Arduino BLE (Bluedroid) defaults TX power to roughly 0 dBm; the reference NimBLE implementation uses `ESP_PWR_LVL_P9` (+9 dBm, roughly 2.5× the range), which matters on boards with a weak PCB antenna (ESP32-C3 Super Mini) trying to reach a BLE proxy across a room. `ble_telemetry_init()` now calls `BLEDevice::setPower(ESP_PWR_LVL_P9, …)` for both `ESP_BLE_PWR_TYPE_ADV` and `ESP_BLE_PWR_TYPE_DEFAULT`. Init log now reports `(TX +9 dBm)`.
- **ESP32-C3 OOM at boot in AP mode + portal stream stalls on small-RAM SoCs** — the ESP32-C3 Super Mini (~400 KB internal SRAM) could not survive boot into AP mode: softAP + lwIP + AsyncTCP exhausted the heap before `mqtt_sub_store` could `calloc` its topic cache, panicking before the portal came up; even after AP came up, portal asset streams stalled because the 4 KB `HTTP_STREAM_CHUNK_SIZE` could not be satisfied from the fragmented DMA-internal heap left after DHCP/DNS pools allocated. Fixes: (1) `app.ino` now skips sensor / BLE / MQTT subsystem init in AP mode, reserving RAM for softAP + portal; (2) `esp32c3-withsensors` `board_overrides.h` sets `HTTP_STREAM_CHUNK_SIZE=1024` (4× less DMA-internal pressure per chunk) and `AP_MAX_CONNECTIONS=1` (honored via `WiFi.softAP()` in `web_portal_ap.cpp`); (3) `portal_nav.js` populates the version badge and starts health polling on first nav so headless / AP landings show fresh values immediately.
- **Dummy sensor showed up in HA Diagnostics tab as a string** — the `dummy_sensor` HA discovery payload set `entity_category="diagnostic"` and omitted `state_class`, so HA placed the entity in the Diagnostics tab and treated the value as a non-numeric string (no history, no graphs). Now uses `state_class="measurement"` and `entity_category=nullptr` to match the BME280 sensor pattern: the entity appears in the main device entity list and HA enables history + graphs.

Display, touch, and screensaver remain fully responsive during any WiFi outage. ### Changed

- **Volume button action no longer persists to NVS** — volume changes from the `volume` button action are now session-only, matching the new brightness action behavior. Volume resets to the NVS-saved value on reboot.

### Fixed

- **Widget animation stuck on rapid bindings** — bar chart and gauge widgets appeared frozen when their data binding resolved faster than the configured animation duration (e.g. `[time:%ms]` every ~10–20 ms vs 300 ms ease-out). Each `lv_anim_start()` replaced the running animation and reset the ease-out curve before any visible progress. Widgets now track the last update timestamp and fall back to direct-set when updates arrive faster than `anim_ms`. Slow-updating bindings (MQTT sensors) still animate smoothly.
- **Compile-time flags report for inheriting boards** — `compile_flags_report.py` now resolves relative `#include` directives in board override files, so boards that inherit from a parent (e.g. `jc4880p433-hx711` including `../jc4880p433/board_overrides.h`) correctly report inherited flags like `HAS_DISPLAY` and driver selectors. Previously these boards showed `(none)` for active features and `—` for driver selectors in build logs and the compile-time flags doc.
- **P4 letterbox scaling black bars** — letterbox mode on ESP32-P4 boards produced unnecessary black bars on both axes because the PPA hardware scaler quantises to m/16 steps, undershooting the ideal scale on most aspect ratios. Replaced PPA with a CPU bilinear RGB565 scaler for letterbox mode while keeping the fast HW JPEG decoder. Cover mode continues to use PPA where quantisation is harmless.
- **PadConfig OOM log flood** — when `buildTiles()` failed to allocate PadConfig or binding arrays, it returned without setting `tilesBuilt`, causing the LVGL task to retry every frame (~30 Hz) and flood the serial log. Now marks `tilesBuilt = true` on OOM so the error logs once per config generation change.
- **Template-inherited icons showing wrong image** — pads using a template pad could display stale or wrong icons for inherited buttons after editing. The icon cache retained old page-local entries even after icon files were deleted, and the preload path skipped refresh for keys already in cache. Fixed by invalidating page-prefixed cache entries when page icons are deleted and always reconciling preloaded icons from the current on-disk or template source.
- **Health table builder missing board config include** — `health_table_builder.cpp` was missing `#include "board_config.h"`, which defines the `HAS_DISPLAY` guard used at the top of the file. Could cause compilation failures depending on include order.

### Fixed
- **Image decoder heap safety** — four hardening fixes for the JPEG/PNG → RGB565 pipeline that address a sporadic `CORRUPT HEAP` crash (1-byte off-by-one overflow):
  - JPEG output callback now clips MCU blocks at the image boundary instead of dropping them entirely (tjpgd can deliver blocks extending past image dimensions due to 8/16-pixel MCU alignment)
  - tjpgd work buffer increased from 4 KB to 8 KB for additional margin on complex JPEGs
  - Letterbox scaling clamps `scaled_w`/`scaled_h` to the target dimensions (floating-point rounding could push them 1 px past the output buffer)
  - JPEG intermediate RGB888 buffer now freed with `heap_caps_free()` consistently (was using `free()` for a `heap_caps_malloc` allocation)
- **Phantom touch on screensaver wake** — tapping to wake the screen no longer triggers a click on the underlying screen; after touch suppression ends, a genuine release is now required before new presses are accepted (fixes stale GT911 touch state leaking through)
- **Rounded corners with image backgrounds** — pad button background images are now clipped to each tile's configured corner radius, so image-backed buttons visually match rounded button styling
- **Pad button border default** — new/unspecified button `border_width` now defaults to `0 px` (was `1 px`) in both firmware parsing and web editor defaults
- **Screen flicker on pad save with icons** — on MIPI-DSI boards (`DISPLAY_BLANK_ON_SAVE`), the browser now blanks the backlight for the entire save sequence (icon delete → icon uploads → config save → tile rebuild) and restores it after LVGL has rendered the new state, eliminating cyan/blue flashes caused by PSRAM bus contention between the DPI controller's continuous DMA scan and heavy LittleFS/lodepng I/O
- **Icon upload race condition** — a stale `errored` flag from a prior failed icon upload could silently block all subsequent icon uploads in the same pad save, causing icons to appear missing until reboot; the flag is now cleared at the start of each new upload
- **Pad config save requiring double-click** — the generation counter was incremented before the RAM cache was updated, so LVGL's polling task could rebuild tiles from stale data; cache is now written before the generation bump, ensuring a single save always renders the correct state
- **Splash spinner animation** — LVGL 9 spinner arc sweep changed from 60° to 270° (LVGL 9 requires 180–360° for smooth animation; 60° caused visible jumping)
- **WiFi MAC crash during image fetch** — `WiFiClient` was stack-allocated on the PSRAM-backed fetch task stack; the WiFi MAC DMA engine could access stale/freed memory from the client's internal lwIP structures after `http.end()` returned but before the stack frame was reused, corrupting TX descriptors (Guru Meditation `LoadProhibited` in `ppTask`). Fix: heap-allocate WiFi clients in internal RAM and add a 100 ms drain delay after `http.end()` to let the MAC finish processing TCP close frames before client destruction
